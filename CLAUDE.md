# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`@lilypad/libs` is a TypeScript utility library (cache, Postgres gateway, logger, flow control, serializer, singleton helpers). It is published from `dist/`. It has no runtime dependency: `postgres` (porsager/postgres) is an optional peer dependency, needed by the `db` entry only (and a dev dependency for the tests).

## Commands

- `npm run build`: tsdown (rolldown) bundles the entries (`src/index.ts` and `src/entries/*.ts`) into `dist/`, as CJS (`.cjs`, `.d.cts`) and ESM (`.mjs`, `.d.mts`), with sourcemaps; the shared chunks go to `dist/chunks/`. The CJS output is forced strict (`outputOptions.strict`). The config is loaded with `unrun` (`--config-loader unrun`), whatever the Node.js version. `dist/` must be byte-identical on every OS: check a build change against a Linux build (e.g. in a `node:22` container).
- `npm test`: vitest projects `unit` and `edge`. `edge` runs the tests of the edge-compatible modules again in the `edge-runtime` environment. Watch mode in a TTY, so use `npm test -- --run` for a single pass.
- `npm run test:integration`: `*.integration.test.ts` files (vitest project `integration`). They start a PostgreSQL container with testcontainers, so **Docker must be running**. They are not part of `npm test` or of the pre-commit hook.
- Single file: `npx vitest run src/cache/LilypadCache.test.ts`
- Single test by name: `npx vitest run --project unit -t "should store and retrieve a value"`
- `npm run typecheck`: `tsc --noEmit` (with `noUncheckedIndexedAccess`). It also checks the `@ts-expect-error` type tests (`LilypadSerializer.test.ts`, the public API test of `LilypadDbCache.test.ts`), which vitest does not.
- `npm run lint`: runs `eslint --fix`, so it **modifies files**. Use `npx eslint . --max-warnings 0` to check without changing anything, as the hook does.

**Pre-commit hook** (`.husky/pre-commit`): stashes the unstaged changes and untracked files (except `dist/`), runs unit tests, typecheck, `eslint --max-warnings 0` and the build on what is being committed, then `git add dist`, and restores the stash. So `dist/` is committed and rebuilt on every commit (the package is installed from git), while lint fixes are **not** staged automatically: run `npm run lint` before committing.

**CI** (`.github/workflows/ci.yml`): the same checks on Node.js 22 and 24, `git diff --exit-code -- dist` after the build, and the integration tests.

ESLint uses `recommended-type-checked`; the test files turn off `require-await`, `unbound-method` and the `no-unsafe-*` rules.

Commit messages use conventional prefixes (`feat:`, `fix:`, `refactor:`, `chore:`).

Files are LF: when a script rewrites a file on Windows, write it with `newline='\n'` (Python) or equivalent.

## Architecture

### Public surface
- Each module has an entry in `src/entries/` (`logger`, `cache`, `flow`, `serializer`, `singleton`, `platform`, `db`), published as a subpath (`@lilypad/libs/logger`, ...). `src/index.ts` re-exports every entry **except `db`**, so that the root entry never pulls in postgres.js. A new class or type must be exported from its entry, or it will not ship. An entry also needs its line in `tsdown.config.ts` and in the `exports` of `package.json`.
- Exported classes keep the `Lilypad` prefix. Everything is exported by name: no default exports.
- **Edge compatibility**: every entry except `db` must not reach Node.js APIs (`node:*`) or `postgres`. `src/entries/entries.test.ts` follows the value imports of each entry and fails otherwise, and the `edge` vitest project runs their tests in an edge runtime (its `include` list must name the test folders of new edge modules, e.g. `src/internal/`). Use `globalThis.crypto` rather than `node:crypto`; `LilypadDbCache` lives in `db`, since it imports the gate.

### Path aliases
The only alias is `@/*` → `src/*`. It is defined in **two places that must stay in sync**: `tsconfig.json` `paths` and `vitest.config.ts` `resolve.alias`.

### Shared internals (`src/internal/`)
- `assertNumberOption(owner, name, value, 'positive' | 'non-negative' | 'positive-integer' | 'non-negative-integer')` checks the numeric options in the constructors (a `NaN` would otherwise pass every comparison). Per-call TTLs are not checked: tests use negative ones to create expired entries.
- `LilypadBackoff`: `fail()` / `succeed()` / `ready(now)`, exponential from a base delay up to one minute. Used for the lazy `LISTEN`, the changelog reads and the schema check.

### Construction and singleton pattern
`LilypadLogger`, `LilypadDbGate` and `LilypadDbCache` have **private constructors**. You create them through a static `create()`:
- It takes `LilypadSingletonAble` options: `{ singleton: true, singletonIdentifier }` or `{ singleton?: false }`.
- Singletons are stored in a map on `globalThis.__lilypadSingletonMap` (`src/singleton/LilypadSingleton.ts`), so they survive module reloads and duplicate bundles.
- The `create()` methods go through `createLilypadSingletonAble` (logger) or `createLilypadSingletonAbleAsync` (gate, cache), which namespace the registry key with the class name (`LilypadDbGate:<id>`) and pass the factory a **release function**. The instance stores it and calls it in `close()`/`dispose()`: it removes the registry entry once, and only while it still holds that instance (or its creation promise): it cannot remove a newer instance registered under the same key. It is a no-op for non-singletons.
- They pass a signature (a hash of the relevant options), so that a later call with different options logs a warning (with the class name as first `libLog` argument). Signatures live in a separate map, `__lilypadSingletonSignatureMap`, so that older bundles sharing the registry can still read it.
- `LilypadDbGate.create` and `LilypadDbCache.create` are async (when they have listeners, with an eager `listen` strategy, they register their LISTEN before resolving) and use `getLilypadSingletonInstanceAsync`. Without listeners they open no connection, which keeps `next build` from reaching the database. That function caches the in-flight promise so concurrent callers share one initialization, and it evicts the promise if initialization fails.
- `LilypadCache` (`new LilypadCache({ ttl, ... })`), `LilypadFlowControl` and `LilypadSerializer` use plain `new`. `LilypadDbCache.create({ ttl, gate, schema, ... })` takes the TTL in its options too, and infers the row type and the primary key column from `schema`.

### Platform capabilities
`src/platform/LilypadPlatform.ts` declares what the library can use from a hosting platform, without depending on any: `background` (keep the instance alive for a promise: `waitUntil`/`after`), `afterResponse` (run work after the response), `shared` (a `LilypadSharedStore`: `get`/`set` with `ttl` in **seconds**/`delete`, a subset of the Vercel Runtime Cache) and `onInvalidate`. Never import `next/*` or `@vercel/*` in the library: `docs/nextjs-vercel.md` shows the adapter the application writes.
- `runInBackground` and `runAfterResponse` always attach an error handler, and fall back to running the work at once if the platform function throws (e.g. `after` outside a request).
- `sharedStoreOperation` bounds every shared store call with a timeout; a failure resolves to a fallback. The shared store is never required to answer.

### Logger
- `LilypadLogger<T>` creates one async method per channel name in `components` at runtime (for example `logger.info(...)`). `T` defaults to `'error' | 'warn' | 'info' | 'debug'`.
- `LilypadLoggerType<T>` is the class type intersected with those channel methods. Use it as the type for logger instances; do not use `LilypadLogger<T>` for this.
- Channel names that clash with a property of the logger (`components`, `register`, `flush`, `name`, `then`, `constructor`, ...) are rejected.
- Output sinks extend `LilypadLoggerComponent` and implement `write(record)` (the only extension point; `formatRecord(record)` gives the text line). See `logger/components/`.
- Every other module takes an optional logger typed `LilypadLibLogger` (`src/logger/LilypadLibLogger.ts`): any object with some of the methods `error`, `warn`, `info`, `debug` (a `LilypadLogger`, `console`, pino). Modules log only through `libLog(this.logger, 'error', this.name, ...)`, which skips missing levels and swallows throws and rejections. The first argument is the `name` of the instance (the class name before an instance exists).
- Messages are formatted by `formatLogValue` (edge-compatible, close to `util.inspect`: errors keep stack, own properties and `cause`; it never throws). The logger option `redact` (default `LILYPAD_DEFAULT_REDACTED_KEYS`, `false` for none) replaces the values of those keys with `[Redacted]` at any depth, in the message (`formatLogValue(value, redaction)`) and in a copy of the context (`redactLogValue`); keys are compared ignoring case, `-` and `_`; `record.parts` stay raw. `safeJson` tracks the ancestors only: a repeated, non-circular reference is printed twice.
- `platform.background` receives every message being sent; `flush()` awaits the pending ones. `context()` is read synchronously when the message is logged.
- Channel methods return promises and are called fire-and-forget. `@typescript-eslint/no-floating-promises` is an error, because an unhandled rejection terminates the Node.js process. For the same reason, channel methods must never reject: component errors (collected with `allSettled`) go to `errorLogging` (sync or async), and if `errorLogging` fails the logger falls back to `console.error`.
- `LilypadDiscordLogger` queues messages and batches them (`minRequestInterval`). It retries a 429 response after `retry-after` (not beyond 30 s: then the batch fails). A failed batch rejects one message only (an error counting the lost messages, with `cause`), so `errorLogging` gets one error per batch. The queue holds at most `maxQueueSize` messages: the oldest are dropped (resolved, not rejected) and announced in the next batch.

### Flow control
`LilypadFlowControl` is **not generic**: `executeFn<T>`, `singleFlight<T>`, `executeWithTimeout<R>` and `executeWithRetries<T>` are typed per call, so one instance runs executions of different types. The primitives are separate (`singleFlight(key, fn)`, `rateLimit(key)`, `executeWithTimeout`, `executeWithRetries`); `executeFn` composes them (`consumerIdentifier` optional, no `errorFn`: callers `.catch`). Single-flight relies on no `await` between the lookup and the registration of the promise (so `rateLimit` stays synchronous). The constructor checks its numeric options.

### How the modules depend on each other
```
LilypadCache ───extends──┐
                         ├──> LilypadCacheCore ──uses──> LilypadFlowControl (single-flight + timeout),
LilypadDbCache ─extends──┘                               LilypadSharedLevel (L2)
      ├──uses──> a sync strategy (cache/dbSync/): LilypadListenSync | LilypadChangelogSync | lilypadNoSync
      ├──uses──> LilypadSchemaVerifier (cache/dbSync/)
      └──uses──> LilypadDbGate (postgres.js, LISTEN/NOTIFY, heartbeat)
```
- **LilypadCacheCore** (`src/cache/LilypadCacheCore.ts`, types in `LilypadCacheTypes.ts`) is the engine: an in-memory, TTL-based cache with `string | number` keys (`LilypadCacheKey`). Its public methods only read, expire or remove (`get`, `peek`, `invalidate`, `delete`, `clear`, `purgeExpired`, protected keys, `dispose`). The value writes and bulk reads (`set`, `bulkSet`, `getOrSet`, `getOrSetDetailed`, `bulkSync`, `getMany`, `entries`, `getAllEntries`) are **protected**: **LilypadCache** (`LilypadCache.ts`) re-declares them public (`getAllEntries` as `getAll`, plus `invalidateBulkSync()`), `LilypadDbCache` keeps them internal so that its values always come from its table.
  - Return values: `undefined` means not cached (or expired), and `null` means cached as "does not exist". Keep this distinction.
  - Options: `ttl`, `errorTtl`, `fetchTimeout`, `bulkSync: { fn, ttl, timeout }`, `staleWhileRevalidate`, `failureCooldown`, `maxEntries`, `cleanupOnAccessEvery`, `autoCleanupInterval`, `shared`, `platform`, `name`, `tagPrefix`, `logger`. All numeric ones are checked by the constructor.
  - `getOrSet` deduplicates concurrent fetches with `flowControl.singleFlight`, keyed per cache key; the flight logs a failure and records it for the cooldown, once. Only the fetch is shared: the error fallback (`errorReturn`, driven by the read option `onError: { fallback: 'stale' | fn, ttl }`) runs for each caller, outside the flight. The fallback function receives `{ key, error, stale }` and returns `undefined` to rethrow. A fallback that is the stale value keeps its `fetchedAt`. A value resolved after the flow control timeout is not cached.
  - **Write ordering**: every entry carries a `ticket`. An async read calls `beginRead()` when it starts, and stores its result with `read.store` (`setIfNewer`, this instance only) or `read.storeFetched` (also L2, ends the cooldown), which discard the result if a write that started later has already been stored. `setIfNewer` and `storeFetched` are private: every new async read path must go through `beginRead()`. A plain write (`set` → `setValue` → `writeLocal`) takes a new ticket; subclasses write with `setValue` (no disposed assertion). A completed bulk sync raises `ticketFloor`, so that older reads of missing keys are discarded too. Per-key `fences` play the same role for a key without an entry while a read of it is in flight (`hasReadInFlight`, extended by subclasses): expiring a key with no entry sets one, and **removing an entry** (`dropEntry`: `delete`, `clear`, purge, eviction, bulk sync, `removeExpired`) keeps the entry's ticket as one. Every removal must go through `removeEntry`/`dropEntry`, never `store.delete` directly.
  - `bulkSync` has its own flow control (`bulkSync.timeout`) and TTL (`bulkSync.ttl`), and uses `bulkSyncFn` (from `bulkSync.fn`). Replacing the content with a complete load is the protected `replaceEntries(read, data)`, which `LilypadDbCache` calls from its own table load. Without one it resolves to `false` (rejects with `throwOnError`) and logs nothing. It resolves to a boolean. Its errors are logged and swallowed, unless `throwOnError` is set. To force a sync, call `forceNextBulkSync()` (public as `invalidateBulkSync()`) instead of writing `bulkSyncExpirationTime`: it also stops a sync that is already running from marking itself fresh. `entries()` leaves out expired or removed entries, so anything that expires or removes a synced entry while the bulk sync is fresh must force the next one (`clear`, `maxEntries` evictions, and `writeEntry` of a value that expires before the bulk sync do). The bulk sync never stays fresh longer than `ttl`, the lifetime of its entries.
  - `get()` does not remove expired entries by default: the expired value is the fallback for `onError: { fallback: 'stale' }`.
  - The store and the protected keys are keyed by `normalizeKey(key)`, the string form of the key. Each entry keeps the original key, which `entries()` returns. Internal iterations work on normalized keys (`removeEntry`, `expireNormalized`), over a **copy** of the store. With `maxEntries`, the LRU order is `evictionOrder` (a `Set` of the unprotected stored keys, least recently used first, updated by `markUsed`, `dropEntry` and the protected-key methods), so evictions never scan protected keys.
  - A disposed cache ignores every internal write (`disposed` flag; `writeEntry` returns `false`, and L2 is written only for stored entries), so that fetches still in flight cannot fill it again, and **every public method throws** (`assertNotDisposed`), except `dispose()`, which returns a promise in every class and is idempotent. Public methods that the engine also needs internally have a non-asserting twin (`purgeExpired`/`purgeEntries`, `clear`/`clearEntries`, `set`/`setValue`, `invalidateBulkSync`/`forceNextBulkSync`).
  - `getOrSet` is a wrapper of `getOrSetDetailed`, which returns `{ value, status, refreshFailed }`. A fresh `fallback` entry is returned with `refreshFailed: true`, and with `failureCooldown` it is refreshed in the background once the cooldown is over (`freshHit`). Lookup order: L1 (memory) → L2 (`shared`, with `name` required) → stale value within `staleWhileRevalidate` (refreshed via `runAfterResponse`, one per key; a refresh that never starts stops blocking after 60 s) → fetch. During `failureCooldown`, the fetch is skipped and `errorReturn` runs with a `LilypadCacheCooldownError`.
  - Entries carry `fetchedAt` (age for L2 adoption), `expirationTime` and `origin` (`source`: a fetch or a write; `fallback`: `errorReturn`; `shared`: adopted from L2). `expire` sets `expirationTime` to `0` and `invalidatedAt`: an invalidated entry is never served stale, but stays a fallback for `onError`, and `adoptShared` refuses L2 copies fetched before `invalidatedAt`.
  - `writeEntry` calls the protected hook `onValueStored(entry)` for each new value (not for `expire`). `expireEverything()` expires every entry and raises `ticketFloor`, discarding the reads in flight; `rejectSharedBefore(time)` stops adopting older L2 values.
  - **L2** is `LilypadSharedLevel` (`src/cache/LilypadSharedLevel.ts`): keys `lilypad:2:<enc(name)>:<kind>:<enc(key)>` with kind `v` (value), `f` (failedAt), `l` (lock), URI-encoded so that no key collides with another; envelope `{ lilypad: 2, value, fetchedAt, expiresAt }`; `lilypadCacheTags` builds the tags (`<tagPrefix>:<enc(name)>`, `...:<enc(key)>`). Bump the format version if it changes. L2 writes: public `set`/`bulkSet` and `storeFetched` (fetches) write L2; fallbacks and bulk syncs do not. A fetched value is kept in L2 through the larger of the cache's and the read's `staleWhileRevalidate`. The codec runs inside the L2 operations: an `encode` or `decode` that throws is a warning and a miss, never a failed read or fetch. A write does not read L2 first unless `shared.checkBeforeWrite`. `delete` and `invalidate` (via `markInvalid`) remove from L2; `clear`/`dispose` do not.
  - `emitInvalidation(source, keys)` calls `platform.onInvalidate` in the background; the engine emits `manual` from `invalidate`.
  - Protected keys are not removed by `delete`/`clear`/purge unless you pass `force`.
  - `expire(key)` is the data part of `invalidate` (without the L2 removal, the bulk sync and the event). `invalidate` is synchronous in every class.
- **LilypadDbCache** (`src/cache/LilypadDbCache.ts`) is a cache on the engine backed by one table described by a `LilypadDbSchema<V, PK>`. Generics `<V, PK, K = LilypadDbKey<V, PK>>`, where `LilypadDbKey<V, PK> = V[PK] & LilypadCacheKey`. Public: `get` and `peek` (with renewal), `getOrFetch`/`getOrFetchDetailed`, `getAll`, `refresh`, `invalidate`, `delete`, `clear`, `purgeExpired`, protected keys, `sqlCreate`/`sqlUpdate`/`sqlDelete`, `dispose`. Options: the cache options without `bulkSync.fn`, plus `gate`, `schema`, `sync`.
  - `loadTable` is single-flight (`tableLoad`, bounded by `bulkSync.timeout`); `loadRows` loads the whole table (with the timeout signal), calls `replaceEntries`, and replaces `members`: the keys of the rows of the table, each with a ticket. After the first load, `onValueStored` (non-fallback values: row → member, `null` → removed), `addMember` (INSERT/UPDATE of a key not cached) and `applyTruncate` keep them up to date; `purge`, eviction and `clear` do not touch them.
  - `getAll()` loads the table when `isTableLoaded()` is false (never loaded, loaded before the sync became trusted, or with `none` after `bulkSync.ttl`), then fetches the stale or missing members with `selectFromTableByPrimaryKeys` (`fetchRows`, L1 only), or reloads if they exceed 25% of the members. It never relies on the freshness of the engine's bulk sync. `getAll(keys)` fetches only those keys. The result is built from the store **and** from the rows the load (`loadTable` returns them) and `fetchRows` just read, since `maxEntries` may have evicted them. `fetchRows` is single-flight per key (`rowFetches`).
  - **Sync strategies** (`src/cache/dbSync/`): the cache builds one `LilypadDbSyncStrategy` (`start`, `beforeRead`, `trustedSince`, `seesOwnWrites`, `dispose`) and gives it a `LilypadDbSyncHost` (closures over `applyChange`, `applyTruncate`, `expireEverything`, `emitInvalidation`, `forgetOwnWritesCoveredBy`, ...). `listen` → `LilypadListenSync` (default; `connect: 'lazy'` defers LISTEN to the first read; `onNotification` is called after the change is applied, `applyChanges: false` leaves the cache to it), `changelog` → `LilypadChangelogSync`, `none` → `lilypadNoSync`. `beforeRead()` returns `undefined` when there is nothing to wait for, and the reads await it **inline** (`const syncing = ...; if (syncing) await syncing;`), so that they stay synchronous up to the fetch registration: never wrap it in an `async` helper. Failed changelog reads, lazy LISTEN and schema checks back off (`LilypadBackoff`).
  - **Trust and renewal**: `sync.trustedSince()` is when `LISTEN` became active (reset on reconnect; `undefined` while `gate.isListenHealthy()` is false, or if `applyChanges: false`) or when the changelog chain started (`undefined` beyond `maxGap`). `renew()` extends an entry past its TTL, without a query, if its `origin` is `source`, it is not invalidated (`expirationTime > 0`), `fetchedAt >= trustedSince` and it is younger than `sync.maxAge`. `get`, `peek`, `getOrFetchDetailed` and `getAll` renew before reading. L2 lifetimes are never extended.
  - `refresh(key)` re-fetches the row (`fetchRow`, with `fetchTimeout`). Calls are coalesced per key (`refreshes`): one running query, plus at most one queued after it for the calls made meanwhile.
  - `sqlCreate`/`sqlUpdate`/`sqlDelete` write through to the database with the gate's CRUD methods (which return the `xid`), then cache the row returned by the database, so generated primary keys work. `storeWritten` takes a ticket before the write: if the entry changed during the write, it expires it instead of caching the row; if the cache was disposed meanwhile, it does nothing. Otherwise it caches with `setValue` (a new ticket, so reads started before lose) and records the write's `xid` in `ownWrites`; a change with that `xid` is skipped while the entry still holds the last own write. Deletions are cached as `null`, which also applies to protected keys; `sqlDelete` resolves to whether a row was deleted. `sqlCreate` returns, uncached and with a warning, a row the `selectSanitizationFn` returns without its primary key.
  - **Changes**: `applyChange(op, id, mode, xid)`. Changelog changes are `lazy` (trusted: only the triggers write the changelog): a DELETE of a held key caches `null` (of a key not held: no entry, only `members` and L2 are cleared, so mass deletes do not evict), an INSERT/UPDATE of a held key is `markInvalid` (whose fence discards a read in flight without a query). Notifications are `eager` and **untrusted** (any role can `NOTIFY`): a change of a held key, DELETE included, re-reads the row (`refreshInBatch`: the keys notified in the same microtask are re-read with one `selectFromTableByPrimaryKeys` through `queryRows(keys, true)`, which stores with `storeFetched`; a failed batch expires its keys; `eagerReads` counts them for `hasReadInFlight`); a DELETE of a key not held caches nothing (`getAll` re-reads its member); a TRUNCATE notification (`applyTruncate('eager')`) marks the table as not loaded instead of empty. Every INSERT/UPDATE calls `addMember`. `TRUNCATE` from the changelog (statement trigger, `row_id` NULL) empties the members with no query. A failed `apply` of the changelog keeps the cursor and backs off.
  - **Changelog** (`src/dbGate/LilypadChangelog.ts`): triggers write `(xid, table_name, row_id, op)` rows. Since version 4, one statement trigger per event with transition tables (`lilypad_old`/`lilypad_new`, `LILYPAD_CHANGELOG_OLD_ROWS`/`NEW_ROWS`) records all the rows of a statement with one `EXECUTE`d `INSERT ... SELECT` that reads only the primary key; the function keeps a `TG_LEVEL = 'ROW'` branch for the row triggers of version 3. Rows with a NULL `row_id` that are not a TRUNCATE are skipped by the reader. `readLilypadChangesBatch` returns, for each request, the rows of the transactions the previous read could not see: the cursor is `LilypadChangelogCursor = { xmax, xip }` (`pg_snapshot_xmax` / `pg_snapshot_xip` of the read's snapshot) and the next read asks for `xid >= xmax OR xid = ANY(xip)`. Each change is returned by exactly one cursor read, whatever the commit order and however long a transaction runs, so there is no dedup of applied changes. `lilypadCursorCovers(cursor, xid)` prunes `ownWrites`. `readLilypadChanges` is the one-table wrapper. The caches of a gate subscribe to one `LilypadChangelogReader` per changelog table (`src/dbGate/LilypadChangelogReader.ts`, a `WeakMap` keyed by gate), which reads every subscribed table in one query and calls each cache's `apply` with its own request (cursor or lookback). Without a trusted cursor (first read, or more than `maxGap` since the last one) it reads a time `lookback` and expires every entry. Notifications of version 3 carry `xid`. The trigger records `TG_TABLE_SCHEMA` too (`table_schema`, `schema` in the payload), and the reader resolves the table with `to_regclass`; rows without a schema (version 1) match any schema. The trigger function carries its version in its comment (`LILYPAD_CHANGELOG_VERSION`): bump it when the generated SQL changes. Pruning: `pruneLilypadChangelog` (from the app), `lilypadChangelogPruneScheduleSql` (a pg_cron job), or the `prune` option of `lilypadChangelogSql`: the trigger calls a `SECURITY DEFINER` `<changelog>_prune()` function on about one statement in `every`, only in `READ COMMITTED`. The options are recorded in a `lilypad-prune:` comment of the trigger function, which the schema check reads back (`installedLilypadChangelogPrune`) so that its fixes keep them. Without `prune`, the output only gains a `DROP FUNCTION IF EXISTS` of the prune function, which is why the version stayed at 4.
  - **Schema check** (`src/dbGate/LilypadSchemaCheck.ts`): `readLilypadSchemaFacts` reads the catalogs only, `evaluateLilypadSchema` (pure, unit-tested) turns the facts into problems, `checkLilypadSchema` does both. The cache runs it through `LilypadSchemaVerifier` once per instance (`sync.verify`): `warn` before LISTEN (it resolves the schema used to filter notifications) or in the background with the first changelog read; `throw` in `create`. With `warn`, a check that could not run (an error, not problems found) is forgotten, and a later read runs it again in the background after a backoff (`checkInBackground`). The changelog check requires the enabled (`tgenabled IN ('O','A')`) changelog triggers to record INSERT, UPDATE and DELETE together: row triggers, or statement triggers with the right transition tables (`recordedEvents`). The `listen` check requires the notifying triggers to cover the three events (possibly split across triggers; a statement trigger counts only if it is a changelog trigger). The unit tests mock it, as they mock `readLilypadChangesBatch`.
  - With the `listen` strategy, it registers a listener on the Postgres channel **`cache_events`**, with a `callbackId` that includes the instance id. `parseLilypadNotification` validates the JSON payloads `{ table, id, op: 'INSERT'|'UPDATE'|'DELETE'|'TRUNCATE', schema?, xid? }`, where `id` is a string or a number (absent for TRUNCATE); anything else is ignored with a warning. `resolveNotifiedKey` keeps the type of a known key, or converts a string id to a number when `cols[primaryKey].type` is `'number'`. INSERT and UPDATE re-fetch only the keys that are cached or being fetched; any other key is only added to `members`. On `onReconnect`, every entry is expired. The listener callback and `onReconnect` do nothing once the cache is disposed; `dispose()` awaits a LISTEN still starting before removing the listener, and a LISTEN that completes after `dispose()` removes itself. The database-side trigger that sends these payloads is not part of the library; `LilypadDbGate.integration.test.ts` contains a reference implementation.
- **LilypadDbGate** wraps postgres.js.
  - The main `sql` client uses `prepare: false`. Keep it that way; it was deliberately removed in a recent commit. The `statementTimeout` option (default 30 s, `false` to leave the database setting) sets Postgres `statement_timeout` on this client: the cache's timeouts do not cancel queries, so this frees the pool. `close({ timeout })` (default 5 s) is idempotent (same promise) and makes the CRUD methods and `addListener` throw (`assertOpen`).
  - Do not cancel queries with the postgres.js `.cancel()`: in 3.4.x it drops the promise of the cancel request, so a failed cancel connection becomes an unhandled rejection.
  - LISTEN goes through postgres.js `listen()`, which opens its own dedicated connection per client (no pool options needed). The gate listens on `sql`, or on a second client when `listenerConnectionString` differs from `connectionString`.
  - **Heartbeat** (`LilypadListenHeartbeat`, option `listenHeartbeat`, default 15 s, `false` to disable): while channels are listened to, the gate listens on `lilypad_heartbeat_<id>` and sends itself `pg_notify` through the main pool; `isListenHealthy()` is true while a beat came back within 2.5 intervals. The heartbeat timer starts only if `heartbeatStop` still holds its own LISTEN (a stop during the start wins), and a failed start is retried by `isListenHealthy()` after a `LilypadBackoff`. postgres.js gives no signal while the listen connection is down (its internal listen client overrides `onclose`), which is why it exists.
  - Callbacks are grouped by channel and keyed by `callbackId`, so re-adding the same id replaces the old callback. Callbacks may be async: their errors are caught and logged. `removeListener` UNLISTENs the channel when its last callback is removed, stops the heartbeat with the last channel, and never rejects.
  - postgres.js calls `onlisten` on the first LISTEN and again after every reconnection. From the second call on, the gate runs the optional `onReconnect` of each callback.
  - The CRUD helpers are generic over `LilypadDbSchema<T, PK>` (`PK` defaults to `keyof T`), and their first parameter is named `schema`. `generatedPrimaryKey` leaves the primary key out of inserts. The column type `bigint` keeps string keys. Rows are mapped to `T` with `selectSanitizationFn`, or by copying the `cols` keys. Writes go through `writeSanitizationFn`, whose result **replaces** the data, so it can remove properties. The `cols` metadata is optional; only the `type` of the primary key is read (by `LilypadDbCache`). `sql` is `readonly`.
  - Only the `cols` keys are selected and returned (unless there is a `selectSanitizationFn`, which gets `*`) and written: extra properties of the data are dropped on purpose, to prevent mass assignment. `undefined` values are not written.
  - `selectAllFromTable(schema, { signal })` reads through a cursor, in batches of 1000 rows, and stops (closing the cursor) once the signal is aborted. `selectFromTableByPrimaryKeys` reads several keys with `IN`, one query per 1000 keys.
  - `insertToTable`/`updateToTable` return `{ row, xid }` and `deleteFromTable` returns `{ deleted, xid? }`: they add `pg_current_xact_id()::text AS __lilypad_xid` to `RETURNING` (the same function as the changelog's `xid` default) and strip it before `mapRow`. `updateToTable` throws `LilypadDbNotFoundError` when no row matches.

### Tests
Tests live next to the sources as `*.test.ts`.
- `LilypadDbCache.test.ts` uses an in-memory fake of `LilypadDbGate` (with `isListenHealthy`), and mocks `readLilypadChangesBatch` (`changelog.batch`, which delegates each request to `changelog.read`); its cursors are built with `at(xmax, xip?)`. A notification test that expects a deletion must delete the row from the fake too: the cache re-reads it.
- `LilypadCache.shared.test.ts` covers L2 (including its key format), stale-while-revalidate and the cooldown with an in-memory fake store that clones values.
- `LilypadDbGate` is covered by the integration tests, which run against a real PostgreSQL (including the changelog, its out-of-order commit and long-transaction tests, and the heartbeat), and by `LilypadDbGate.test.ts` for what needs no database (pool options, no connection on create). `LilypadChangelogReader.test.ts`, `LilypadSchemaCheck.test.ts` (on `evaluateLilypadSchema`) and `LilypadListenHeartbeat.test.ts` need no database either.
- The flow control tests use fake timers (`withFakeTimers` helper). The cache tests all run on fake timers (`vi.advanceTimersByTimeAsync`).
- `LilypadPlatform.test.ts` covers the fallbacks of `runInBackground`/`runAfterResponse`. The platform tests run in the `edge` project too.
