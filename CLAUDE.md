# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`@lilypad-studio/libs` is an internal TypeScript utility library of Lilypad Studio (cache, Postgres gateway, logger, flow control, serializer, singleton helpers). It is ES modules only, for Node.js 22.12+ (which also loads them with `require()`), and is published to **GitHub Packages** (`publishConfig.registry`; the scope must be the GitHub owner, `Lilypad-Studio`) by the release workflow: `dist/` is never committed. It has no runtime dependency: `postgres` (porsager/postgres) is an optional peer dependency, needed by the `db` entry and the `lilypad-doctor` command only (and a dev dependency for the tests).

The development tools need Node.js 22.22.1+, 24.11+ or 26+ (`devEngines`, from the `engines` of lint-staged and tsdown; `.nvmrc`: 24) and npm. `@types/node` stays on 22.12 (`~22.12.0`, and Dependabot skips its minor updates), so that the typecheck rejects the Node.js APIs the lowest supported version lacks.

## Commands

- `npm run build`: tsdown (rolldown) bundles the entries (`src/index.ts`, `src/entries/*.ts` and the command `src/cli/lilypad-doctor.ts`) into `dist/`, as ESM (`.mjs`, `.d.mts`, declarations generated by oxc thanks to `isolatedDeclarations`) with sourcemaps; the shared chunks go to `dist/chunks/`. One format only, so one copy of each class. It **rewrites the `exports` and the `bin` of `package.json`** from the entries of `tsdown.config.ts` (never edit them by hand, commit the result), then runs publint, arethetypeswrong (`esm-only`) and unplugin-unused, which fail the build.
- `npm test`: vitest projects `unit` and `edge` (single run; `npm run test:watch` to watch). `edge` runs the tests of the edge-compatible modules (the `edgeFolders` of `edge.config.ts`) again in the `edge-runtime` environment, without the Node.js globals (`vitest.edge-setup.ts` removes `process`, `Buffer`, `setImmediate`...).
- `npm run test:integration`: `*.integration.test.ts` files (vitest project `integration`). They start a PostgreSQL container with testcontainers (`postgres:16-alpine`, or `LILYPAD_TEST_PG_IMAGE`), so **Docker must be running**. They are not part of `npm test` or of the pre-commit hook.
- Single file: `npx vitest run src/cache/LilypadCache.test.ts`
- Single test by name: `npx vitest run --project unit -t "should store and retrieve a value"`
- `npm run typecheck`: `tsc -p tsconfig.json` (everything, with `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`, `isolatedDeclarations`), then `tsc -p tsconfig.edge.json` (the root entry and every entry except `db`, with the `webworker` lib and **no Node.js types**: `process`, `Buffer` or `node:*` in an edge module fail it). It also checks the `@ts-expect-error` type tests (`LilypadSerializer.test.ts`, the public API test of `LilypadDbCache.test.ts`, ...), which vitest does not.
- `npm run lint` checks (`--max-warnings 0`); `npm run lint:fix` applies the fixes. `npm run format` / `format:check`: Prettier, which formats every file (ESLint does not format: `eslint-config-prettier`).
- `npm run knip`: unused files, exports and dependencies. `npm run coverage`: v8 coverage of the unit tests; `npm run coverage:all` adds the integration tests (Docker), which cover the gate. `npm run docs:api`: TypeDoc API reference in `api-docs/` (ignored).
- `npm run check`: everything CI checks except the integration tests.
- `node dist/lilypad-doctor.mjs --help`: the `lilypad-doctor` command (package.json `bin`), after a build. It loads a config file (`lilypad.config.*` or `lilypad.<name>.config.*` in the working directory, or `--config <name|path>`); a `.ts` config needs Node.js 22.18+ (or `--experimental-strip-types`).
- `npx changeset`: records a user-facing change (bump + CHANGELOG entry, in the sections of CHANGELOG.md: `#### Upgrading` table, `#### Added`...). Refactors, tests and tooling need none. The release workflow runs `npm run changeset:version` (`changeset version`, then `scripts/merge-changelog-sections.ts` merges the sections of the changesets into one per kind, and the lockfile gets the version). See `docs/releasing.md`.

**Hooks** (husky): pre-commit runs lint-staged (ESLint `--fix` and Prettier on the staged files, fixes staged), then `npm run typecheck` and `npm test`; commit-msg runs commitlint (conventional commits: `feat:`, `fix:`, `refactor:`, `chore:`, ...).

**CI** (`.github/workflows/ci.yml`, on pull requests, and called by the release workflow on every push to `main`): format, lint, typecheck, tests, build (with its package checks), `git diff --exit-code -- package.json` (the generated `exports`), knip on Node.js 22, 24 and 26 (`npm audit` and `npm pack` on 24 only); the packed tarball installed in an empty project on Node.js **22.12.0** (with `postgres@3.4.9`, the lowest version of the peer dependency) and loaded with `import` and `require()` by `scripts/smoke-test.mjs`; the integration tests on 22, 24 and 26 (PostgreSQL 16, the lowest supported version), and on 24 with PostgreSQL 18. **Release** (`.github/workflows/release.yml`): runs CI (`workflow_call`) and goes on only if it passes; changesets then opens the "chore: version packages" PR, and publishes to GitHub Packages once it is merged. Actions are pinned by SHA; Dependabot updates them and the npm dependencies.

ESLint uses typescript-eslint `strictTypeChecked` + `stylisticTypeChecked` (`projectService`), import-x (`no-cycle`, `no-extraneous-dependencies`) and the vitest plugin; `eslint.config.mjs` explains each rule it turns off. The edge modules may not import `node:*`, `postgres` or the `nodeOnlyFolders` of `edge.config.ts`, by alias or relative path (`@typescript-eslint/no-restricted-imports`), nor use `import()` (`no-restricted-syntax`: the typecheck resolves `import('postgres')`). Object types are declared with `type`, not `interface`.

Files are LF: when a script rewrites a file on Windows, write it with `newline='\n'` (Python) or equivalent.

## Architecture

The detailed notes on each module (the cache engine and its tickets, the database cache and its sync strategies, the changelog, the schema check, the gate, the logger, the tests) are in **[docs/architecture.md](docs/architecture.md)**: read the section of a module before changing it. [docs/how-it-works.md](docs/how-it-works.md) is the guided tour.

### Public surface

- Each module has an entry in `src/entries/` (`logger`, `cache`, `flow`, `serializer`, `singleton`, `platform`, `schema`, `db`), published as a subpath (`@lilypad-studio/libs/logger`, ...). `src/index.ts` re-exports every entry **except `db`**, so that the root entry never pulls in postgres.js; `db` re-exports `schema`. A new class or type must be exported from its entry, or it will not ship. A new entry needs its line in `tsdown.config.ts` (the build adds it to the `exports` of `package.json`: commit it), and in `typedoc.json` `entryPoints` (`src/entries/entries.test.ts` and `tsconfig.edge.json` find the entries themselves); if it is edge-safe, also an `export *` in `src/index.ts`. A new module folder goes in `edgeFolders` or `nodeOnlyFolders` of `edge.config.ts` (`entries.test.ts` fails otherwise): the lint and the vitest `edge` project read that list.
- `src/cli/` holds the `lilypad-doctor` command: `lilypad-doctor.ts` (the entry, with its `#!/usr/bin/env node`, which rolldown keeps) and `LilypadDoctorCli.ts` (argument parsing with `node:util` `parseArgs`: `--config`, `--url`, else the variable `--url-env` (default `DATABASE_URL`) from the environment, then from the `--env-file` files (`util.parseEnv`, never written to `process.env`), `--sql`, `--json`; exit codes 0/1/2; unit-tested with an injected `run`, `load` and `readEnv`. Node.js 22 checks that a `--env-file` given to the script exists, even after the script name: a missing one exits with 9 before the CLI runs). `lilypad-doctor init [--config <name|path>] [--empty] [--force]` (`LilypadInitCli.ts`, dispatched on `argv[0] === 'init'`, no database) writes a config from `lilypadDbConfigTemplate.ts` (TypeScript for `.ts`/`.mts`, JavaScript otherwise); it refuses when a file of the same config exists; `--force` overwrites only the file it creates, never next to another file of the same config (the loader would refuse both). Its tests inject the file system (`init` dependencies) and import every template variant (the package import replaced by `src/entries/schema.ts`), so a template that stops being a valid config fails them. The check itself is `runLilypadDoctor({ connectionString, config })` (`src/dbGate/LilypadDoctor.ts`, exported by `db`, with `lilypadSchemaCheckOptions(config)`).
- Exported classes keep the `Lilypad` prefix. Everything is exported by name: no default exports.
- **Edge compatibility**: every entry except `db` must not reach Node.js APIs (`node:*`) or `postgres` (`db` may reach `postgres`, `node:crypto`, `node:fs`, `node:path`, `node:url`). `src/entries/entries.test.ts` follows the run-time imports of each entry (static, side-effect and `import()`; an import it cannot resolve fails it) and fails otherwise, `tsconfig.edge.json` typechecks them without the Node.js types, the lint forbids those imports and `import()` in the edge files, and the `edge` vitest project runs their tests in an edge runtime without the Node.js globals. The edge folders are listed once, in `edge.config.ts`. Use `globalThis.crypto` rather than `node:crypto`. The folders follow the entries: `src/dbCache/` (`LilypadDbCache`, which imports the gate), `src/dbGate/` and `src/cli/` are Node.js-only, every other folder is edge-safe as a whole.
- Errors are typed: `LilypadDisposedError` (a disposed cache or a closed gate), `LilypadCacheCooldownError`, `LilypadTimeoutError`, `LilypadRateLimitError`, `LilypadDbNotFoundError`, `LilypadDbMissingPrimaryKeyError`, `LilypadDbEmptyWriteError`, `LilypadSchemaCheckError`. Keep their messages stable: tests match them.

### Path aliases

The only alias is `@/*` → `src/*`, defined in `tsconfig.json` `paths` (vitest reads it with `resolve.tsconfigPaths`, tsdown and ESLint with the TypeScript resolver).

### Rules that apply everywhere

- **Types**: every optional property is declared `name?: T | undefined` (`exactOptionalPropertyTypes`: callers may pass `undefined`, which the code treats as a missing option). Exported functions, methods and public fields have explicit types (`isolatedDeclarations`). Types are imported with `import type` / inline `type` (`verbatimModuleSyntax`).
- **Promises**: `@typescript-eslint/no-floating-promises` is an error, because an unhandled rejection terminates the Node.js process. Logger channel methods return `void`, never throw, and never reject in the background.
- **`undefined` means not cached (or expired), `null` means cached as "does not exist"**: keep the distinction.
- **Cache engine**: every async read goes through `beginRead()` and stores with `read.store` / `read.storeFetched`; every removal goes through `removeEntry`/`dropEntry`, never `store.delete`; a read joins a fetch in flight only if its ticket is above `currentTicket(key)`; `beforeRead()` of a sync strategy is awaited inline (`const syncing = ...; if (syncing) await syncing;`), never in an `async` helper. See docs/architecture.md.
- **Gate**: the main `sql` client keeps `prepare: false`; never cancel queries with the postgres.js `.cancel()`.
- **Database configs hold no functions** (the hooks are bound with `bindLilypadDbHooks`), and `src/dbConfig/LilypadPgTypes.ts` is the only place that knows the PostgreSQL types.
- **Versioned formats**: bump `LILYPAD_CHANGELOG_VERSION` (`src/dbGate/LilypadChangelog.ts`) for any change of the objects the changelog SQL installs (an older install is then an error of the schema check), and `SHARED_FORMAT_VERSION` (`src/cache/LilypadSharedLevel.ts`, the `lilypad:2:` keys) for any change of the shared entries. The `db-modules` skill lists the tests to update.
- **Generated files**: `package.json` `exports`/`bin` (tsdown), `CHANGELOG.md` (changesets, from the `.changeset/*.md` files): never edit them by hand.
- The cache and flow control tests run on fake timers (`vi.advanceTimersByTimeAsync`): an assertion on a promise is registered before the timers advance, and awaited after.
