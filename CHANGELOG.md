### Added

- `appRole` option of `defineLilypadDb` (`@lilypad-studio/libs/schema`): the role the application connects as (behind a pooler, the role the pooler connects as), whose privileges and settings `lilypad-doctor` checks. `lilypad-doctor --app-role <name>` overrides it, and so do the `appRole` option of `runLilypadDoctor` and of `checkLilypadSchema` (`@lilypad-studio/libs/db`). It defaults to the role the doctor connects as.

  ```ts
  export default defineLilypadDb({ appRole: 'app_user', tables: { users } });
  ```

- `lilypad-doctor` checks what the library assumes of the database and never verified:
  - the role of the application: its privileges on the tables, their schemas and the changelog (`missing-privilege`, with the `GRANT`); its settings, as PostgreSQL applies them at login (`replica-replication-role`, `pruning-isolation` when the trigger prunes the changelog only in `READ COMMITTED`, `idle-session-timeout` with a `listen` table, `read-only-database`); row-level security on a cached table (`row-level-security`);
  - the changelog functions: their owner may write the changelog (`changelog-function-owner`), they are still `SECURITY DEFINER` with their `search_path`, and `PUBLIC` may not execute them (`unsafe-changelog-function`);
  - the changelog table: no row-level security, a nullable `row_id`, and its `(table_name, xid)` and `(changed_at)` indexes (`changelog-shape`);
  - the writes the triggers do not see: a cached partition, whose statement triggers miss the writes made through its partitioned table (`partition-table`), the partitions and inheritance children of a table (`child-tables`), a table that logical replication writes without its triggers enabled `ALWAYS` (`replicated-table`);
  - the server: a standby (`read-only-database`), a `NOTIFY` queue half full (`notify-queue-usage`).
- `lilypad-doctor` creates the role of the application. Set `appRole` in the config (`defineLilypadDb`, `@lilypad-studio/libs/schema`) to a role that does not exist yet, and run `lilypad-doctor --sql` with the owner's URL: the fix of `missing-app-role` creates it unless it exists (without a password, since the migrations are committed: set it with `ALTER ROLE app_user PASSWORD '...'` or the console of your provider), with its `statement_timeout` and only what the tables of the config need: `USAGE` on their schemas, `SELECT` of their described columns, the writes of `LilypadDbCache` (`INSERT` and `UPDATE` of the described columns, `DELETE`, `USAGE` on the sequences of their serial columns), and `SELECT` on the changelog of the `changelog` strategy; the fix of a missing table grants it the table it creates. Then connect the application as it; when the config gains a table or a column, `missing-privilege` reports the `GRANT` it needs.

  ```ts
  export default defineLilypadDb({ appRole: 'app_user', tables: { users, plans } });
  ```

- `access` option of a table (`defineLilypadTable`, `@lilypad-studio/libs/schema`): `'read'` when the application only reads the table. The role the doctor creates gets no write of it, and the doctor no longer reports the writes it lacks. Defaults to `'write'`. Type `LilypadDbTableAccess`.
- With `strict: true`, `lilypad-doctor` warns when the role of the application has more privileges than the tables need (`privileged-app-role`): a superuser, `CREATEROLE`, `BYPASSRLS`, or the privileges of the owner of a cached table or of the changelog. `checkLilypadSchema` (`@lilypad-studio/libs/db`) takes it as its `strict` option.
- `lilypad-doctor` checks the `statement_timeout` of the role it connects as (with the database and server settings, and what the connection sets), and warns (`long-statement-timeout`) when there is none or it is longer than `maxStatementTimeout`. The gate sets no timeout by default, and a cache that stops waiting (`fetchTimeout`) does not stop its query: without a timeout, a query stuck on a lock or a dead connection holds its connection of the pool, and the writes of `LilypadDbCache` (`sqlCreate`, `sqlUpdate`, `sqlDelete`) wait with it. The warning has no fix SQL, since the doctor may run as another role than the application: its message gives the `ALTER ROLE ... SET statement_timeout` to run, and says where the current value comes from (the default, the server configuration, the database, the role, the connection).
- `maxStatementTimeout` option of `defineLilypadDb` (`@lilypad-studio/libs/schema`): the longest `statement_timeout` the doctor accepts, in ms (default: 1 minute), or `false` to skip the check. `checkLilypadSchema` takes it as an option too; run on the gate of the application, it also sees the gate's `statementTimeout`.

### Fixed

- The changelog trigger function (`lilypadChangelogSql`, `@lilypad-studio/libs/db`) can no longer be made to run another role's code as its owner. It reads the transition tables `lilypad_old` / `lilypad_new` by their unqualified names; for a statement trigger that does not declare them, PostgreSQL resolved those names in `pg_temp`, so a role granted `EXECUTE` on the function (which `CREATE TRIGGER` needs, e.g. the role of the migrations) could attach it, without `REFERENCING`, to a table of its own, and have it read a temporary view of its session: the functions of that view ran with the privileges of the changelog owner, a superuser when a superuser installed the changelog. The function now checks in `pg_trigger` that the firing trigger declares the transition tables of its event, and raises otherwise.
- `lilypad-doctor` no longer fails (exit code 2) when the role it connects as lacks `USAGE` on the schema of a cached table: it resolves the qualified tables through the catalogs, and reports the missing privilege.

- `writable-changelog` no longer reports the `DELETE` that `pruneLilypadChangelog` needs with `changelog: { pruning: 'external' }`, and its fix no longer revokes it: running the doctor's SQL broke the pruning from the application that the Next.js guide shows.
- `LilypadDbGate` (`@lilypad-studio/libs/db`) works behind PgBouncer with its default options: it no longer sends the `statement_timeout` startup parameter unless `statementTimeout` is given (see Upgrading).
- `LilypadDbCache` (`@lilypad-studio/libs/db`) with the `changelog` strategy and `poll: 'await'` waits for a read of the changelog at most its `fetchTimeout`. Nothing bounded that query (the gate sets no `statement_timeout` by default), so a changelog query stuck on a lock, a full pool or a dead connection held every `getOrFetch`, `getAll` and `getManyOrFetch` of the caches of the gate, rows already in memory included, ignoring their `timeout` and `onError`. A read that times out is logged as `Error reading the changelog:` (a `LilypadTimeoutError`) and goes on with the content of the cache, as after a failed read; the changelog read keeps running, and applies its changes if it completes.
- `LilypadLogger` (`@lilypad-studio/libs/logger`) no longer blocks the event loop on a crafted logged value. Its channel methods, `toLogJson` and the messages the other modules log through it mask the passwords of URLs (`scheme://user:[Redacted]@host`). The expression that finds them backtracked quadratically on a long run like `a.a.a…://`: a 50 KB value took about 4 seconds to format, and it was formatted synchronously by the channel method. Such a value can come from user input that a logged error carries, e.g. a PostgreSQL error that quotes the invalid input. Formatting is now linear. A URL scheme longer than 64 characters is no longer masked.
- `lilypad-doctor` (and `checkLilypadSchema`, `runLilypadDoctor` in `@lilypad-studio/libs/db`) no longer installs version 9 of the changelog where it fails the writes of a table outside the checked config. The check withheld the changelog fixes only for the tables of the config whose key the version 9 triggers refuse, but every table whose changelog triggers record into the same changelog goes through that trigger function: a table of another config or service sharing the changelog, or a table removed from the config. On an older install, the fix of `outdated-changelog` (or of a notify, trigger or pruning problem) installed version 9, and every write of such a table then failed. The check now reads the other tables whose enabled changelog triggers record a missing key column or a key of a type the triggers refuse, reports each one (`unsupported-key-type` or `missing-column`, an error, with its `schema.table` as `table`), and withholds the fixes of the changelog, its triggers and its privileges until they are changed, as for a table of the config. If you upgraded to version 9 already, run `lilypad-doctor` again: a table it now reports fails its writes; change its key, or reinstall its triggers with its primary key (`lilypadChangelogTriggerSql`), or drop them.

### Added

- `LilypadTimeoutError` is exported by `@lilypad-studio/libs/cache` and `@lilypad-studio/libs/db` too (the same class as in `/flow`), and `LilypadCacheCooldownError` by `@lilypad-studio/libs/db`: `getOrSet`, `getOrFetch`, `refresh` and `getAll` throw them, and they can now be tested with `instanceof` from the entry of the cache, e.g. `import { LilypadTimeoutError } from '@lilypad-studio/libs/db'`.
- `normalizeLilypadPgType` and `LILYPAD_DEFAULT_CHANGELOG_TABLE` are exported by `@lilypad-studio/libs/schema` (and so by `@lilypad-studio/libs`), next to `lilypadColumnTypesOfPgType` and `LILYPAD_DEFAULT_DB_CONFIG_NAME`. `@lilypad-studio/libs/db` still exports them.
- `LilypadLogger.dispose()` (`@lilypad-studio/libs/logger`) waits for the messages logged so far, as `flush()` does, then removes a singleton logger from the registry, so that the next `LilypadLogger.create({ singleton })` with its identifier builds a new logger. `await using logger = LilypadLogger.create(...)` calls it at the end of the scope. The logger holds no resources: its channel methods keep working afterwards.
- The option types `LilypadLoggerOptions` (`@lilypad-studio/libs/logger`) and `LilypadSerializerOptions` (`@lilypad-studio/libs/serializer`), named like the options of the other classes (`LilypadCacheOptions`, `LilypadDbGateOptions`, ...).
- `lilypad-doctor --fail-on-warnings`: exits with 1 when the check reports warnings, not only errors, so that a CI job or a deployment step fails on anything the database lacks.
- `LilypadRateLimitError.rateKey` (`@lilypad-studio/libs/flow`): the limited key (`<consumer>#<function>`, or the function alone), which was only in the message.
- The schema check (`lilypad-doctor`, `runLilypadDoctor`, `checkLilypadSchema` in `@lilypad-studio/libs/db`) reports `newer-changelog`, a warning, when the changelog trigger function was installed by a newer version of the library than the one running the check. The message says to upgrade `@lilypad-studio/libs`.
- `LilypadSchemaProblem.fixDatabase` (`@lilypad-studio/libs/db`): the database a `fix` must run in, when it is not the checked one (the pg_cron job scheduled from the database pg_cron runs in). `lilypad-doctor --sql` leaves these fixes out of the migration, as comments under `-- Run in the database "<name>", not in this one:`, and the report shows them under `Run this SQL in the database "<name>":`. Before, `--sql` mixed them into the migration, which then failed at `CREATE EXTENSION pg_cron`.
- The schema check reports `unsupported-key-type` (an error): a cached table (a `changelog` table, or a `listen` table that the changelog triggers notify or would notify after the fix) whose primary key has a type the changelog triggers cannot convert as their owner — an enum or base type not owned by a superuser, or whose output or json cast function is not, a user-defined (non-built-in) composite, range or multirange type, or an array or domain over one. Until the key is changed (or a missing key column restored, `missing-column`), the check withholds every fix of the changelog, its triggers and its privileges, and says so in their messages. `LilypadSchemaProblemCode` (`@lilypad-studio/libs/db`) has this new member.
- `LilypadDbTable.selectByPrimaryKeys(keys, { signal })` (`@lilypad-studio/libs/db`) stops before its next batch of 1000 keys once the signal is aborted, as `selectAll` does.
- The schema check reports `writable-changelog` (a warning): a role other than its owner may write the changelog. Its fix revokes it, after the changelog SQL when that is outdated too. `LilypadSchemaProblemCode` has this new member.

### Changed

- Deprecated: `LilypadLoggerConstructorOptions` and `LilypadSerializerConstructorOptions` are aliases of `LilypadLoggerOptions` and `LilypadSerializerOptions`, kept until 1.0. Replace `LilypadLoggerConstructorOptions<T>` with `LilypadLoggerOptions<T>`, and `LilypadSerializerConstructorOptions<FROM, TO, KeyMap>` with `LilypadSerializerOptions<FROM, TO, KeyMap>`.
- A `LilypadDbCache` with the `listen` strategy applies at most 2000 notifications per second, and one `TRUNCATE` or `BULK`: beyond, it applies the others as one change of the whole table, at once and at the end of the second. Anyone connected to the database can send a notification: a flood of them used to cost, for each notified key, a removal from the shared level, an invalidation event and memory, and for each `TRUNCATE`, an expiration of every entry.
- A cache remembers at most 10,000 invalidations of keys it does not hold (for its shared level); beyond, it refuses every shared copy produced before them instead, in constant memory.
- The warning about a malformed `cache_events` notification is logged at most once a minute, with the number of the others.
- The logger masks the password of the URLs in every logged string, message and stack (`postgres://user:[Redacted]@host/db`), unless `redact` is `false` (an empty list of keys keeps the masking). `LilypadLogRecord` has a new `errors` field: the Error objects of the message, redacted the same way, which `LilypadJsonConsoleLogger` now writes instead of the raw ones.
- The message of `outdated-changelog` no longer lists what each older version lacks: it gives the installed version and the expected one. A changelog table whose `table_schema` column was dropped is reported as such, instead of as an older version.
- A `LilypadDbCache` with the `listen` strategy (`@lilypad-studio/libs/db`) sends a `notification` event with `keys: []` and the tag of the cache to `platform.onInvalidate` when `LISTEN` is re-established, since the notifications sent while it was down are lost.

### Fixed

- `new LilypadDbTable(gate, definition)` (`@lilypad-studio/libs/db`) checks the definition and applies the hooks bound to its table on the config of the gate (`bindLilypadDbHooks`), as `gate.table(definition)` does. It used to accept any object, and to skip those hooks, so a `write` hook that sanitizes the data was silently not applied.
- The declarations of the package no longer add `__lilypadSingletonMap` and `__lilypadSingletonSignatureMap` to the global types of the application.
- `LilypadDbGate.assertOpen()` is marked internal, and no longer listed in the API reference: use `gate.closed`.
- The API reference lists the config functions and types (`defineLilypadDb`, `LilypadDbSchema`...) under `@lilypad-studio/libs/schema`, the entry a config file imports, instead of `@lilypad-studio/libs/db`.
- README: `LilypadDbGate.create` and `LilypadDbCache.create` open a connection only with `listen` channels or an eager `listen` sync; the channel methods of a logger return nothing; the name of the instance is the `source` of the meta given to the logger of the other modules; `LilypadFlowControl` takes no `logger`.
- The Quick Start of the README compiles: its logger can be passed to the gate and the cache (see Upgrading). The README gives the type of the `write` hook as it is, `LilypadDbPartialRow<T>` (a function typed `(data: Partial<T>) => Partial<T>` is rejected under `exactOptionalPropertyTypes`), and splits the config and the application of its first `LilypadDbCache` sample, which did not compile as one block.
- `getOrSet` with `onError`: the fallback of a fetch started before an `invalidate` no longer replaces the value of a newer fetch. The cache used to keep the pre-invalidation value (a `'stale'` fallback) for `errorTtl`, and discard the fresh one.
- Invalidating a key that is already invalidated (`invalidate`, or two quick changes of the same row in `LilypadDbCache`) now discards the fetch of the key started in between. The value that fetch read before the second change used to be cached as fresh for the whole TTL.
- A shared cache no longer picks up the old shared copy of a key that `invalidate` or `delete` removed while the removal from the shared store failed or was still under way, when the key had no local entry or its invalidated entry was purged. `LilypadDbCache` gets the same protection for the keys it does not hold, when a change of their row removes their shared copy.
- A shared entry whose `fetchedAt` or `expiresAt` is not finite, or whose `value` is `undefined` (possible with a store that does not go through JSON), is ignored with a warning, instead of being cached forever. A shared failure time that is not finite is ignored, and one in the future (another instance's clock ahead) counts as now, so that the `failureCooldown` of a key cannot last forever.
- The failure, fence and refresh bookkeeping of a cache stays bounded without `purgeExpired` (no `autoCleanupInterval` or `cleanupOnAccessEvery`): it used to keep every distinct key whose fetch had failed, beyond `maxEntries`. A `STALE` value whose refresh failed now stays reported with `refreshFailed: true` after `purgeExpired`.
- A disposed cache no longer records failed fetches in the shared level (a fetch cut short by a shutdown put the other instances in `failureCooldown`), no longer starts a `staleWhileRevalidate` refresh scheduled before `dispose()`, and a `getOrSet` disposed while it read the shared level rejects with `LilypadDisposedError` instead of fetching.
- With `maxEntries`, invalidating an entry no longer makes it the most recently used one, and `removeProtectedKeys` evicts at once the entries beyond the limit.
- `LilypadCache` (`@lilypad-studio/libs/cache`): a bulk sync no longer caches, for a whole TTL, the value it read before an `invalidate()` of a key the cache did not hold.
- `LilypadCache`: a bulk sync no longer counts as fresh beyond the expiration of an entry written while it ran (by `set`, `getOrSet` or the shared level). `getAll()` used to leave that key out once it expired, until the end of `bulkSync.ttl`.
- `LilypadCache` and `LilypadDbCache` (`@lilypad-studio/libs/db`) with a shared level: a key invalidated while the removal of its shared copy failed no longer adopts that old copy once a newer value written to this instance only (a bulk sync, or a table load of `LilypadDbCache`) is removed by `clear()`, an eviction or a purge.
- With `refreshLockTtl`, a stale-while-revalidate refresh reads the lock again when it starts. With `platform.afterResponse` it starts after the response, and every instance that served the stale value meanwhile used to refresh it too. A cache disposed while its refresh takes the lock no longer fetches.
- With `failureCooldown` and a shared level, the failure times read from the shared level stay bounded without `purgeExpired`: an instance kept every distinct key that failed on another instance.
- After a step back of the system clock, the `failureCooldown` of a key that failed just before no longer lasts as long as the step: the failure time then counts as now, as for a failure read from the shared level.
- With a `staleWhileRevalidate` longer than the time since 1970 (e.g. `Number.MAX_SAFE_INTEGER`), an invalidated entry is no longer served as `STALE`, and `purgeExpired()` removes it.
- `lilypad-doctor` no longer reports a false `column-type-mismatch` error for a `pgType` that PostgreSQL writes differently: `numeric(10)` (`numeric(10,0)`), `bit` (`bit(1)`), `text[][]`, `integer ARRAY`, `integer ARRAY[4]` and `integer[3]` (all `integer[]`: PostgreSQL ignores the dimensions of an array), `dec(10,2)` and `char varying(10)`. `normalizeLilypadPgType` (`@lilypad-studio/libs/schema`) now writes them as `format_type` does.
- The type `LilypadDbHooks` (`@lilypad-studio/libs/schema`) accepts `undefined` for the hooks of a table, as `bindLilypadDbHooks` does at runtime (the table is left as it is), under `exactOptionalPropertyTypes`.
- The docs say that a config is trusted code: `pgType`, `default: { sql }` and the `expression` of a check are not checked, and go as they are into the SQL that `lilypad-doctor` prints (the library never runs it).
- The table definitions of `defineLilypadDb` are frozen all the way down, and hold copies of the columns, references and lists of the input: changing the input (or a column object shared by two tables) after `defineLilypadDb` no longer changes the definitions.
- `bindLilypadDbHooks` keeps a hook bound before when it is given as `undefined` (`{ write: undefined, select }` used to remove `write`), and leaves a table given no hook as it is: an empty `hooks` hid the hooks of the gate's config from that definition.
- `lilypad-doctor` judges a column of a domain by the type the domain is based on (through nested domains), as postgres.js reads it: a domain over `int8`, `numeric` or `time` declared `'string'` no longer gets a warning, and one declared `'number'` gets it. The domain's category (`N`, `D`), which it used, holds types that postgres.js reads differently.
- `lilypad-doctor` reads `pgType: 'float(p)'` as PostgreSQL does, `real` up to 24 and `double precision` above, instead of reporting a type mismatch.
- `loadLilypadDbConfig` reports the load failure of a config module that throws `null` or `undefined`, instead of a `TypeError`.
- `lilypadChangelogTriggerSql` (changelog SQL version 9, see Upgrading) no longer loses the INSERT, UPDATE and DELETE triggers of a table whose name is long (from about 54 characters, schema included). PostgreSQL truncated the four trigger names to the same 63 bytes, so each trigger replaced the previous one and only `TRUNCATE` was recorded, even after the fix SQL of `lilypad-doctor`. A name that PostgreSQL would truncate is now shortened with a hash, and the SQL drops the truncated triggers of earlier versions.
- With the `prune` option of `lilypadChangelogSql`, the `SECURITY DEFINER` function `<changelog>_prune()` no longer searches `pg_temp` first: any role that could connect could create a temporary table of the changelog's name, call the function, and run its own trigger code with the privileges of the function's owner. Reinstall the changelog SQL (see Upgrading, version 9) now if you use `prune`.
- The changelog SQL works with table and channel names that contain `$` (for example `$$`): the function bodies are now quoted with a tag the names do not contain. Such a name used to make the migration fail with a syntax error.
- `LilypadDbTable.selectAll` (and so the full loads of `LilypadDbCache`) no longer fails with `canceling statement due to statement timeout` when reading the whole table takes longer than the gate's `statementTimeout` (30 s by default). The timeout now bounds each batch of 1000 rows, not the whole read: `selectAll` reads through an SQL cursor (`DECLARE`, then `FETCH`) in one transaction, so a pooler in statement mode is no longer supported for it, and the time a `select` hook spends between batches counts toward `idle_in_transaction_session_timeout`.
- `LilypadDbGate` no longer repeats notifications and `onReconnect` calls after a `LISTEN` that failed, for example during a database outage. postgres.js kept the listener of each failed attempt and listened to it again on every reconnection. Each notification then ran the callbacks once more per failed attempt, and each reconnection resynchronized the caches as many times, including the callbacks removed since.
- `isListenHealthy()` no longer reports a dead `LISTEN` connection as healthy after the system clock steps back: the heartbeat now measures time on the monotonic clock. Without a heartbeat (`listenHeartbeat: false`), it is `true` only once `LISTEN` is active on a channel, not while it is still starting.
- `LilypadDbGate.create` with an existing `singleton` now logs its warning when the `listen` option differs (by `channel` or `callbackId`). The listeners of that call were ignored without a word: add them with `addListener`.
- The changelog SQL (version 9: run `lilypadChangelogSql` and `lilypadChangelogTriggerSql` again, see its Upgrading row) works whatever the name of the changelog table and of its schema. A name that contained one of the placeholders of its SQL (`__lilypad_changelog__`, `__lilypad_prune__`...) installed a trigger function that failed every write to the cached tables. A name of 62 characters or more (schema included) made PostgreSQL truncate two of its functions, and two of its indexes, into one name: without `prune`, the SQL dropped its own trigger function (and failed on a reinstall); with `prune`, it failed; and the index on `changed_at` was never created. Those names are now cut with a hash, and the SQL drops the index that the earlier versions created under the truncated name; shorter names, and the default name of the pg_cron job of `lilypadChangelogPruneScheduleSql`, do not change.
- `lilypadChangelogSql` and `LilypadDbGate.addListener` reject an empty channel, or one longer than 63 bytes. `pg_notify` rejects such a channel, so the trigger failed every write to the cached tables; `LISTEN` truncates it, so its notifications were never delivered.
- `LilypadDbTable.selectByPrimaryKeys` returns the row of a key given several times once. A key that fell in two of its batches of 1000 keys returned its row twice.
- The `LilypadFlowControl` rate limit uses the monotonic clock (`performance.now()`). A step back of the system clock (an NTP correction, a resumed VM) used to refuse every recorded key until the clock caught up. `rate: 0` no longer records anything.
- The retries of the lazy `LISTEN`, of the changelog reads and of the gate heartbeat are no longer postponed by a step back of the system clock. They also keep retrying after more than 1024 consecutive failures.
- Background work (`platform.background`, `platform.afterResponse`) can no longer become an unhandled rejection, which terminates the Node.js process, when its error handler throws.
- A shared cache (`platform.shared`) never receives a `NaN` or `Infinity` TTL: a non-finite TTL becomes 1 second.
- `LilypadFlowControl` (`@lilypad-studio/libs/flow`): a timed out attempt always rejects with a `LilypadTimeoutError`, as documented. A `fn` whose promise rejects from its abort listener with an error of its own (for example `reject(new DOMException('Aborted', 'AbortError'))`) used to replace it, so `shouldRetry` and the callers' `instanceof LilypadTimeoutError` checks saw that error instead.
- `LilypadFlowControl.executeFn` checks the per-call `timeout` before the first attempt, like `retries`: an invalid one (`NaN`, `0`, more than 2^31 - 1 ms) rejected with a `RangeError` only after being retried with backoff and passed to `shouldRetry`. A call with an invalid `timeout` or `retries` no longer uses the rate limit of its key, so the next valid call is not refused with a `LilypadRateLimitError`. Both options are checked for a call that joins one in flight too: its options are still ignored, but an invalid one now rejects it with a `RangeError` (the running call is unaffected), instead of failing only when no call is running.
- `LilypadCache` and `LilypadDbCache` (`@lilypad-studio/libs/cache`, `@lilypad-studio/libs/db`): a stale-while-revalidate refresh runs once when `platform.afterResponse` throws after scheduling it. The fallback used to start it a second time.
- `LilypadLogger` (`@lilypad-studio/libs/logger`): a message with an `Error` part whose `stack`, `message` or `name` cannot be read (a getter that throws, such as a failing `Error.prepareStackTrace`) or is not a string is logged. It used to be lost: no component received it, and `errorLogging` got an internal `TypeError` instead. `record.errors` converts such a field to a string, and replaces one that cannot be read (`Error` for the name, an empty message, no stack). In the text of the message, such an error used to print as `[Unformattable value]`, and an error whose `cause` getter threw as well: they now keep the rest of the error, with `[cause]: [Getter threw]`.
- `LilypadLogger`: a typed array, such as a Node.js `Buffer`, prints as `Uint8Array(3) [ 1, 2, 3 ]`, its first 100 items, without listing all its keys first: logging a 5 MB `Buffer` blocked the caller for about 500 ms to print `{ '0': 0, '1': 0, ... }`. The JSON form (`toLogJson`, the context, `LilypadJsonConsoleLogger`) is unchanged.
- `LilypadLogger`: the `redact` option also applies to the `cause` of errors, as it does to the `errors` of an `AggregateError`: with `redact: [...LILYPAD_DEFAULT_REDACTED_KEYS, 'cause']`, the causes print as `[Redacted]`.
- An `errorLogging` callback that logs on its own `LilypadLogger` (`@lilypad-studio/libs/logger`) no longer loops forever when a component keeps failing. The loop ran in microtasks only, so it hung the process. The failures of the messages that `errorLogging` logs synchronously now go to `console.error` only. Do not log on the same logger after an `await` inside `errorLogging`.
- A logged value that cannot be read (a `toJSON` or an iterator that throws, a Proxy trap) no longer replaces the whole message part or the whole context with `[Unformattable value]`: only that value does. `record.context` is always an object: a context that does not serialize to one is kept under `context` (`LilypadJsonConsoleLogger` used to write its characters as fields `"0"`, `"1"`...).
- The logger prints the `errors` of an `AggregateError`, e.g. each address that a failed connection to `localhost` tried. They were missing, and the error message is often empty.
- In the text form of logged values, nested strings and quoted keys escape their backslashes, line breaks and control characters as JSON does (`'C:\\Users'`), so a logged value can no longer start a new line of the output.
- `lilypadPinoLogger` follows the level changes of the pino logger it wraps (`logger.level = 'debug'`). It used to keep the level pino had when it was wrapped.
- `LilypadDiscordLogger` measures its throttling on the monotonic clock (`performance.now()`): a step back of the system clock no longer holds the messages, and `logger.flush()`, until the clock catches up. When the retries of a rate limited request run out, the next batch waits for the `retry-after` time given by Discord; beyond 30 seconds, the next batches fail without a request until that time. Truncated messages no longer end with half an emoji. The error of a failed batch no longer counts the "messages dropped" notice as a lost message.
- `LilypadLogger.register` with an inherited name (`constructor`, `toString`) throws `Logger type "..." was not defined...` instead of a `TypeError`.
- When several services share one database, the `lilypad-doctor --sql` of a service still on an older version no longer installs that version's changelog SQL over the newer one. Before, any problem whose fix included the changelog SQL (a missing notify trigger, a missing table with its triggers, the pruning) replaced the trigger function of the newer version with the older one, under every service of the newer version. While the installed changelog is newer, every fix of the changelog, its triggers and its privileges is withheld (as for an unsafe primary key), and the message of each such problem says why. A missing table keeps its `CREATE TABLE`, without its triggers.
- `lilypad-doctor` and `checkLilypadSchema` (`@lilypad-studio/libs/db`) no longer fail with `permission denied for schema cron` when pg_cron is installed and the role of the check has no USAGE on its schema (pg_cron grants it to no role but its owner by default): the jobs are then unknown, as when `cron.job` cannot be read.
- A changelog trigger on a primary key whose name has characters beyond ASCII (e.g. `clé`) or a backslash is no longer reported as `wrong-trigger-primary-key`, which its own fix could not clear.
- The fixes of a config with both `changelog` and `listen` tables install the same changelog SQL: a table's fix no longer reinstalls the changelog without the suggested pruning (which the next check reported again). The changelog function notifies on one channel: a table that needs another one (a per-table `notifyChannel` of `checkLilypadSchema`) gets no fix, and its message says to give it a notifying trigger of its own.
- The `CREATE TABLE` fix of a missing table gives a generated `uuid` primary key (`generatedPrimaryKey`) the default `gen_random_uuid()`, and starts with `CREATE SCHEMA IF NOT EXISTS` when the schema of the table is missing too (the message says so). A default it cannot write (`default: true`, a generated key of another type) is listed as a comment after it, instead of a table that the next check rejects. `missing-column-default` on a generated primary key now has a fix: an identity for an integer key, `gen_random_uuid()` for a `uuid`.
- The pruning check reads the retention of a pg_cron job only when it understands all of its interval: an ISO 8601 interval (`'P1M'`, once read as 1 minute), an unknown unit, a sign or `ago` leaves it unknown, instead of a false `short-changelog-retention` error. `year` and `ms`/`milliseconds` are now understood. Comments in the command of a job are ignored (a commented-out `DELETE` no longer counts as pruning), and its table names are compared as PostgreSQL reads them (a quoted name keeps its case and may contain spaces).
- A changelog function whose comment has the `lilypad-changelog:` prefix but no integer version is reported as `outdated-changelog` (version 1), instead of passing as current.
- `lilypad-doctor` reports `--sql` with `--json`, and an empty `--config`, before it looks for the database URL.
- The `missing-column-default` fix of an integer primary key declared `generatedPrimaryKey` (`lilypad-doctor`, `checkLilypadSchema` of `@lilypad-studio/libs/db`) moves the new identity past the keys the table already has (`SELECT setval(...)` after the `ADD GENERATED BY DEFAULT AS IDENTITY`). Before, the identity started at 1 and the inserts failed on the existing keys.
- The pruning check reads the retention of a pg_cron job only from the one statement of its command that deletes from the changelog, a `DELETE` with one interval. Before, it read the first interval of the whole command: a job that also cleans another table (`DELETE FROM sessions ... interval '30 minutes'; DELETE FROM lilypad_cache_changes ...`) was reported as `short-changelog-retention`, and the fix scheduled it again with the changelog `DELETE` alone, dropping the rest of its command. Only a job whose command is one `DELETE FROM <changelog> WHERE changed_at < now() - <interval>` now gets that fix (any other condition would be lost too); for the others, the message says to change the interval in the job.
- A pg_cron job that deletes from a table of the same name in another schema (`archive.lilypad_cache_changes`) is no longer taken for the pruning of the changelog, whose schema the check knows.
- The commands of the pg_cron jobs are read as PostgreSQL reads them: nested block comments, escape strings (`E'...'`), dollar-quoted strings (literals, except the body of a `DO` block, which is code). A command left open (an unclosed comment or literal) deletes nothing.
- When pg_cron is installed but the role of the check cannot read `cron.job`, the `no-changelog-pruning` message says so, instead of saying that no job of the role deletes the rows.
- `lilypad-doctor init --config ./lilypad.default.config.ts --force` overwrites that file. Before, it was taken for a file of the default config (`lilypad.config.*`, which the loader looks for): `--force` failed with `EEXIST`, and a `lilypad.config.ts` next to it made `init` refuse.
- The changelog trigger function (version 9: run `lilypadChangelogSql` and `lilypadChangelogTriggerSql` again, see the Upgrading rows of version 9) no longer converts a primary key as the changelog owner unless the key type is safe. `to_jsonb` runs the value's cast to `json` or its output function (and recurses into array elements and composite fields), resolved by the type rather than the `search_path`, so a key whose type, output function or a json cast function a non-superuser owns would run that role's code as the changelog owner — ownership of the type alone is not enough. The trigger now fails closed, recording the key only when the key column exists and its type is a built-in type, a base or enum type whose type, output function and json cast functions are owned by superusers, or a domain or array over one; a renamed or dropped key column, a user-defined (non-built-in) composite, range or multirange type, or any other type is refused. `lilypad-doctor` checks the same rule, from one shared SQL fragment.
- A shared cache entry stamped in the future (by an instance whose clock is ahead, or planted in the store) is ignored until its time comes. It used to pass every invalidation made before its stamp, `TRUNCATE` included, and `checkBeforeWrite` never replaced it.
- `LilypadDbCache.getManyOrFetch` and `getAll` stop querying the batches of their keys once they time out.
- `LilypadDiscordLogger` keeps its webhook URL in a private field: it no longer shows up when the logger itself is logged or serialized.
- `lilypad-doctor init` no longer overwrites a config file created after its check, nor writes through a link to a missing file: without `--force`, it creates the file only if nothing is there.
- After a step back of the system clock (an NTP correction, a resumed virtual machine), a `LilypadDbCache` with the `changelog` strategy (`@lilypad-studio/libs/db`) no longer stops reading the changelog, and serving stale rows, until the clock catches up, and no longer keeps trusting its cursor after a gap longer than `maxGap`. `pollInterval` and `maxGap` are now measured on the monotonic clock.
- `LilypadDbCache` with the `changelog` strategy (`@lilypad-studio/libs/db`) keeps a row past its TTL only while a read of the changelog was applied within `pollInterval` (two intervals with `poll: 'background'`). It used to trust the changelog for up to `maxGap` (1 hour by default) after its last read, so `get` and `peek`, which never read the changelog, and reads made while the changelog could not be read, kept serving rows changed since. `getAll` likewise no longer trusts its list of rows then. An application that reads such a cache with `get` alone now sees rows expire at their TTL whenever no `getOrFetch` or `getAll` read the changelog within `pollInterval`: read with `getOrFetch` to keep them without a query.
- A change applied while `LilypadDbCache` loads its table (`getAll`, the first call especially) no longer loses to the load: the row read before the change was cached as up to date, and kept past its TTL, and a row inserted during the first load was missing from every later `getAll`.
- A change made elsewhere while `sqlCreate`, `sqlUpdate` or `sqlDelete` runs no longer loses to the write when the cache did not hold the key: the cache kept the row of its own write, older than the change.
- `LilypadDbCache` bounds its bookkeeping: at most 32 remembered transactions per key written by the instance (none with `listen` and `applyChanges: false`, which applies no notification), and a bounded number of rows noted from notifications (anyone can send one): beyond a quarter of the table, the next `getAll` loads the table again.
- A `refresh` queued behind a running one rejects with a `LilypadDisposedError` if the cache was disposed meanwhile, instead of querying the database.
- `getManyOrFetch(keys)` (formerly `getAll(keys)`, see the `getAll` row of Upgrading) returns a key given twice (e.g. `7` and `'7'`) under its first spelling; a key notified again before its re-read is sent no longer uses the budget of 1000 re-reads per second; `getAll` no longer loads the whole table twice in one call when rows changed during its load.
- `LilypadDbCache.getAll()` (`@lilypad-studio/libs/db`) no longer resolves to an empty or partial table when a change of the whole table reaches the cache while it loads the table (a `BULK` or `TRUNCATE` notification, a `LISTEN` reconnection, a changelog read of more than 1000 rows): it loads the table again.
- `LilypadDbCache.getAll()` no longer rejects at every call after one notification carried an id that the primary key cannot hold (e.g. `"abc"` for an integer key: any role connected to the database can send one), which made the database reject its query by primary keys until the table was loaded again. When that query fails, `getAll()` now loads the whole table instead, once.
- After a step back of the system clock (an NTP correction, a resumed virtual machine), `LilypadCache` and `LilypadDbCache` (`@lilypad-studio/libs/cache`, `@lilypad-studio/libs/db`) no longer stop refreshing a stale key whose background refresh the platform dropped (`platform.afterResponse`), nor stop purging on access (`cleanupOnAccessEvery`), until the clock catches up. Both intervals are now measured on the monotonic clock.
- A `LilypadDbCache` with the `changelog` strategy and a shared level keeps a row in the shared level for at most its `lookback` after reading it (with `lookback: 0`, not at all), whatever the `ttl` or `staleWhileRevalidate` given to `getOrFetch`. When no instance read the changelog for a while (e.g. every serverless instance idle or new), the first read applies only the changes of the `lookback`: a shared copy kept longer, read before an older change, was served as up to date for the rest of its TTL.
- When `LISTEN` is re-established, a `LilypadDbCache` with the `listen` strategy no longer takes from the shared level the rows copied there before, which may predate a lost notification (every instance loses it when the database fails over), and the next `getAll` loads the whole table again. It used to expire only its own entries, so `getAll` on a table that was empty missed the rows inserted while `LISTEN` was down, for up to `bulkSync.ttl`. With the `changelog` strategy, `getAll` likewise loads the whole table again after a broken chain of reads (the first read, or none for `maxGap`), even within `bulkSync.ttl`.
- `LilypadDbCache.getAll` and `getManyOrFetch` no longer cache as missing (`null`) the rows that a `select` hook (`bindLilypadDbHooks`) returns with another primary key, nor load every row without a primary key under one key: those rows are left out, and the keys they may belong to are expired, with a warning naming the hook. `getOrFetch` then returned `null` for rows that exist.
- A `cache_events` notification whose `id` holds a lone surrogate (`"\ud800"`, which no row can have) is ignored as malformed. It used to make the cache log an error (or a shared level warning) at each one, without the once-a-minute limit of the malformed notifications.

- The `type` of a column follows from its `pgType` (`int4` is `'number'`, `int8` `'bigint'`, `timestamptz` `'date'`, `jsonb` `'json'`, `text[]` `'array'`...): declare it only for the types postgres.js has no parser for (enums, domains, extension types). `lilypadColumnTypesOfPgType(pgType)` (`@lilypad-studio/libs/schema`) gives the column types of a PostgreSQL type, and `LilypadDbColumnFor<V>`, `LilypadDbColumnTypeOf<V>`, `LilypadDbColumnValues` and `LilypadPgTypeOf<C>` type the columns of a property type. - `LilypadDbPartialRow<T>` (`@lilypad-studio/libs/schema`): some columns of a row, the type of the data of the `write` hook and of `LilypadDbUpdateData`.

- A fetch of a key that was not cached yet could cache a value read before the key was invalidated or changed.
- An invalidated key could adopt a copy from the shared level produced before the invalidation, if its removal had failed.
- `bulkGet({})` left out an entry written with a TTL shorter than the bulk sync while the sync still counted as fresh.
- A row inserted again elsewhere after being cached as `null` was left out of `getAll()` until the next full load.
- Background refreshes that never started stayed tracked forever; they are now removed by `purgeExpired`.
- `selectFromTableByPrimaryKeys` failed with more than 65 535 keys: it now sends one query per 1 000 keys.
- `formatLogValue` threw on a getter that throws, and the message was lost.
- `LilypadDiscordLogger` did not read the response bodies, which kept connections busy.

## 0.2.0

### Upgrading from 0.0.1

These changes can break existing code. Check each item that applies to you.

| Change | What to do |
| --- | --- |
| Node.js 20 or later is required. | Upgrade Node.js. |
| Singletons created by `create()` are registered under `<Class>:<identifier>` (e.g. `LilypadDbGate:main`). | Code that read them with `getLilypadSingletonInstance('main')` must call `create()` again instead. If two versions of the library run in the same process, each builds its own instances until both are upgraded. |
| `insertSanitizationFn`: its result now **replaces** the data, instead of being merged into it. | A function that returned only the changed fields must now return the whole object (`(data) => ({ ...data, title: data.title?.trim() })`). |
| `getAll()` rejects when the table cannot be loaded (it used to return an empty or partial list). | Catch its error where an empty list was acceptable. |
| `bulkSync()` resolves to a boolean (it resolved to `undefined`). | Only code that checked the result is affected. |
| `LilypadFlowControl.rateLimit()` is synchronous: it throws instead of rejecting. | Replace `await expect(...).rejects` / `.catch()` with `try/catch`. |
| `flowControlTimeout` no longer applies to `bulkSync`, which has its own `bulkSyncTimeout` (30 s). | Set `bulkSyncTimeout` if you relied on `flowControlTimeout` for bulk syncs. |
| `defaultErrorTtl` defaults to the TTL, at most 5 minutes (it was always 5 minutes). | Set it explicitly to keep the former value. |
| The logger no longer uses `util.inspect`: objects are formatted by an internal formatter, close to it (`[Circular]` instead of `[Circular *1]`). | Only code that parsed log messages is affected. |
| A channel named `then` or `flush` is rejected. | Rename the channel. |
| `LilypadDbCache` caches deleted rows as `null` even for protected keys. | None: protected keys were wrongly kept. |
| Notification triggers that the library installs send `id` as a string. | None: the cache accepts numbers and strings. |
| `useDefaultDbListener` and `defaultListenerOptions` are deprecated. | Use `sync: { strategy: 'none' }` or `sync: { strategy: 'listen', listenerOptions }`. They still work. |
| The changelog records the schema of each table (version 2). The changelog of a development build of 0.2.0 must be upgraded. | Run `lilypadChangelogSql()` again (it adds the `table_schema` column). Until then, reads of the changelog fail. |
| `LilypadDbCache` checks once that its triggers are installed (`verify: 'warn'`), and warns on `console.warn` when it has no logger. | Install what the warning lists, or set `sync.verify: 'off'` (for example if you send notifications in a way the check does not see). |

### Added

- **Next.js / Vercel support** without depending on either: see [docs/nextjs-vercel.md](docs/nextjs-vercel.md).
  - `LilypadPlatform` (`background`, `afterResponse`, `shared`, `onInvalidate`), accepted by the logger and the caches.
  - Subpath entries (`@lilypad/libs/logger`, `/cache`, `/flow`, `/serializer`, `/singleton`, `/platform`, `/db`), ESM builds, and edge-runtime compatibility for every module except `/db`.
- **LilypadCache**: a shared level between instances (`shared`, `name`, `codec`, soft refresh lock), `staleWhileRevalidate`, `failureCooldown` (shared between instances), `getOrSetDetailed` with the status of the value, `maxEntries` (LRU), `cleanupOnAccessEvery`, a per-call `timeout`, invalidation events.
- **LilypadDbCache**: the `sync` option, with the `changelog` strategy (a trigger writes every change to a table; each instance reads it at most once per `pollInterval`, missing no commit whatever its order), `listen` with `connect: 'lazy'`, and `none`. Helpers `lilypadChangelogSql`, `lilypadChangelogTriggerSql`, `pruneLilypadChangelog`, `readLilypadChanges`.
- **Schema check**: `checkLilypadSchema` reports what the database misses for the `changelog` and `listen` strategies, with the SQL that fixes it. `LilypadDbCache` runs it once (`sync.verify`: `warn`, `throw` or `off`).
- **LilypadDbGate**: `pool` options, the `lilypadServerlessPool` preset, `statementTimeout`, `onReconnect` on listeners, typed partial updates (`LilypadDbSchema<T, PK>`).
- **Logger**: `platform`, `flush()`, `context`, structured records for components (`sendRecord`), `LilypadJsonConsoleLogger`. `LilypadDiscordLogger` batches messages and retries rate-limited requests.
- **LilypadFlowControl**: per-execution `timeout`, `isInFlight`.
- Numeric cache keys keep their type (`LilypadCacheKey = string | number`).

### Fixed

- `LilypadDbCache` mixed up tables of the same name in different schemas: it applied the changes of `archive.users` to a cache of `users`, with both strategies.
- `insertSanitizationFn` could not remove properties from the written data.
- A failing `errorLogging` callback made the logger reject, which terminated the process.
- Out-of-order refreshes could leave an old row in a `LilypadDbCache`; writes are now ordered by when they started.
- Concurrent `getOrSet` calls shared the error options of the first caller.
- A bulk sync that timed out still overwrote the cache later.
- `LISTEN` subscriptions were not told about reconnections, which lose notifications.
- Properties set to `undefined` made inserts and updates fail.
- Several smaller issues: see the commit history.
