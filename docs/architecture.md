# Architecture notes

Condensed notes on the internals, module by module: what each one guarantees, and the rules a change must keep. [CLAUDE.md](../CLAUDE.md) lists the commands and the rules that apply everywhere; [how-it-works.md](how-it-works.md) is the guided tour.

## Shared internals (`src/internal/`)

- `assertNumberOption(owner, name, value, 'positive' | 'non-negative' | 'positive-integer' | 'non-negative-integer' | 'positive-delay' | 'non-negative-delay')` throws a `RangeError` for an invalid numeric option in the constructors (and for the per-call `retries` of `executeWithRetries`) (a `NaN` would otherwise pass every comparison). Every duration given to a timer uses a `*-delay` rule (at most `LILYPAD_MAX_TIMER_DELAY`, 2^31 - 1 ms: beyond it, or with `NaN`, a timer fires at once), including the per-call `timeout` of `getOrSet` and of `executeWithTimeout`, and the result of `backOffTime`. Per-call TTLs are not checked: tests use negative ones to create expired entries.
- `withLilypadTimeout(operation, timeout, createError)` (`LilypadTimeout.ts`): the only race against a timer (used by `executeWithTimeout` and `sharedStoreOperation`); on timeout it rejects, then aborts the signal with the same error (rejecting first, so that an operation rejecting from its abort listener cannot replace the timeout error), and it always clears the timer.
- `LilypadBackoff`: `fail()` / `succeed()` / `ready()`, exponential from a base delay up to one minute (the exponent is capped, so the delay stays finite even with a zero base). It measures time on the monotonic clock (`performance.now()`), so that a step back of the wall clock does not postpone a retry; callers never pass a time. Used for the lazy `LISTEN`, the changelog reads and the gate heartbeat.

## Construction and singleton pattern

`LilypadLogger`, `LilypadDbGate` and `LilypadDbCache` have **private constructors**. You create them through a static `create()`:

- It takes `LilypadSingletonAble` options: `{ singleton?: string }`, the identifier of the singleton (none: a new instance each time).
- Singletons are stored in a map on `globalThis.__lilypadSingletonMap` (`src/singleton/LilypadSingleton.ts`), so they survive module reloads and duplicate bundles.
- The `create()` methods go through `createLilypadSingletonAble` (logger) or `createLilypadSingletonAbleAsync` (gate, cache), which namespace the registry key with the class name and `SINGLETON_REGISTRY_VERSION` (`lilypadSingletonRegistryKey`: `LilypadDbGate@1:<id>`; bump the version when an instance changes in a way another copy of the library sharing the registry could not use) and pass the factory a **release function**. The instance stores it and calls it in `close()`/`dispose()`: it removes the registry entry once, and only while it still holds that instance (or its creation promise): it cannot remove a newer instance registered under the same key. It is a no-op for non-singletons.
- They pass a signature (a hash of the relevant options), so that a later call with different options logs a warning (with the class name as the source). Signatures live in a separate map, `__lilypadSingletonSignatureMap`, so that older bundles sharing the registry can still read it.
- `LilypadDbGate.create` and `LilypadDbCache.create` are async (when they have listeners, with an eager `listen` strategy, they register their LISTEN before resolving) and use `getLilypadSingletonInstanceAsync`. Without listeners they open no connection, which keeps `next build` from reaching the database. That function caches the in-flight promise so concurrent callers share one initialization, and it evicts the promise if initialization fails.
- `LilypadCache` (`new LilypadCache({ ttl, ... })`), `LilypadFlowControl` and `LilypadSerializer` use plain `new`. `LilypadDbCache.create({ ttl, gate, table, ... })` takes the TTL in its options too, and infers the row type and the primary key column from the table definition (see Database configs).

## Database configs (`src/dbConfig/`, entry `schema`, edge-safe)

The database modules require a config: `defineLilypadDb({ name?, defaultSchema?, notifyChannel?, changelog?: { table, pruning, minRetention }, strict?, tables: { key: defineLilypadTable<T, PK>({...}) } })`. It is imported by the application at runtime (**nothing is compared with the database there**) and loaded by `lilypad-doctor`, which checks the database against it.

- `defineLilypadTable` is an identity function that carries the row type (a phantom `lilypadRowType` key). `defineLilypadDb` runs `validateLilypadDbConfigInput` (the config only, `defineLilypadDb: ...` messages; it throws on the first problem). A JavaScript config is not type-checked, so every object of the config may hold only its options (`optionsOf<T>` lists them, and the compiler checks the list against the type: a new option goes in both), the flags must be booleans, the lists arrays, the objects not arrays (`tables: [orgs]` would give the keys `0`, `1`...), and the identifiers (schemas, table parts, columns, the channel, the names of constraints) at most 63 bytes, without a dot (the library splits the names it quotes on their dots); the channel cannot be a key of `Object.prototype` (postgres.js keeps its channels in a plain object), nor contain `__lilypad_` (`LILYPAD_RESERVED_CHANNEL_PART`, the prefix of the placeholders of the changelog SQL, which `lilypadChangelogSql` refuses in a channel). It then resolves each table into a `LilypadDbTableDefinition<T, PK>`, frozen all the way down (copies of the input's columns, references and lists, so a change of the input does not reach it): `key`, `tableName` (unqualified), `schemaName`, `qualifiedName`, `sync` (default `listen`), `strict`, resolved `unique` (with the column `unique: true`), `foreignKeys` (with the column `references`; the referenced table qualified: an unqualified name is the table of the config of that `tableName` in the default schema, or else its only one, rejected when several schemas share it, or else a table of the default schema outside the config; its columns defaulting to that table's primary key, and checked against its `cols`), `indexes` (`using` default `btree`), `checks`, and `db` (the settings of its config). The default constants are in `LilypadDbConfigDefaults.ts` (a separate module, to avoid a value cycle with the validation).
- **A config holds no functions** (`lilypad-doctor` `import()`s it with Node.js alone, so everything it imports must load without a bundler): `validateLilypadDbConfigInput` rejects `writeSanitizationFn`/`selectSanitizationFn`/`hooks` in a table. The application binds them with `bindLilypadDbHooks(db, { key: { write?, select? } })` (`LilypadDbHooks.ts`, entry `schema`): a frozen copy of the config whose named definitions carry a frozen `hooks` (merged over the bound ones; an `undefined` hook is not given, and a table given none is left as it is), typed by `LilypadDbHooks<C>`. `resolveLilypadDbTable` gives a definition without hooks the hooks of the same table (same key, config name and `qualifiedName`) in the config it resolves against (`withConfigHooks`), so a gate created with the bound config applies them to `db.tables.x` too; no identity check, since singleton gates outlive module reloads. `loadLilypadDbConfig` appends `lilypadConfigLoadHint(error)` to a load failure (a type imported as a value, `ERR_MODULE_NOT_FOUND` and co.; vitest resolves imports more leniently, so the hint is tested on built errors).
- Definitions and configs carry `Symbol.for('lilypad.dbTable')` / `Symbol.for('lilypad.dbConfig')` (shared by every copy of the library). `resolveLilypadDbTable(owner, table, config)` takes a definition or a key (in the `config` of the call, else of the gate) and rejects anything else: `gate.table()` and `LilypadDbCache.create()` use it. Types: `LilypadDbTableDefinitionBase` / `LilypadDbTableInputBase` are the structural "any row type" forms (no `any`: the lint forbids warnings), `LilypadDbTableName<C>`, `LilypadDbRow<C, N>`, `LilypadDbPrimaryKey<C, N>` read a config type.
- Several configs: a gate is created with at most one (`LilypadDbGate<C>`, `config` option); `LilypadDbCache.create` has three overloads (a definition; `config` + key; a key of the gate's config). `loadLilypadDbConfig({ config, cwd })` (`src/dbGate/loadLilypadDbConfig.ts`, Node only, exported by `db`) finds `lilypad.config.{ts,mts,mjs,js}` / `lilypad.<name>.config.*` (an error when several exist) or a path, `import()`s it, takes its default (or `config`) export, and checks that a config found by name has that name.
- Column metadata (`LilypadDbColumn`): `type` (what postgres.js returns; runtime: the primary key's number conversion), `pgType`, `nullable`, `default` (`true | { sql }`), `unique`, `references`, `converted` (types only); only the doctor reads the rest. **`src/dbConfig/LilypadPgTypes.ts` is the only place that knows the PostgreSQL types**: `PG_TYPES` (by `format_type` name: the column types, the first being what postgres.js returns, the `aliases` and the `serials`), `CATEGORY_TYPES` (unknown types, by `typcategory`, the last resort: the doctor judges a domain by its base type, which `LilypadSchemaFacts` resolves through nested domains, since PostgreSQL sends a domain's values as those of its base type), and `LilypadDbColumnValues` (each column type and the JavaScript type of its values; `LilypadDbColumnType` is its keys, `LILYPAD_DB_COLUMN_TYPES` its runtime list). Everything else derives from them: `normalizeLilypadPgType` (the spelling of `format_type`: aliases, the default modifiers `numeric(p,0)`, `bit(1)` and `character(1)`, one `[]` for any array), `lilypadColumnTypesOfPgType`, `lilypadColumnTypeMismatch` (the validation and the doctor's `column-type-mismatch` warning), `isLilypadSerialPgType`/`isLilypadIntegerPgType` (the fix SQL), and the types `LilypadPgTypeOf<C>` (the spellings, with modifiers) and `LilypadDbColumnTypeOf<V>`. Add a type or an alias there, never elsewhere. `defineLilypadDb` fills a missing `type` from `pgType` (`resolveColumns`); `cols` of `defineLilypadTable<T>` is `{ [K in keyof T]-?: LilypadDbColumnFor<T[K]> }` (optional properties too) (a declared `type` must fit `T[K]`; without it, the `pgType` must be a known one that fits; `converted: true` skips the check). The doctor compares `pgType` exactly, and `type` only without `pgType`.
- **A config is trusted code** (a module the application and `lilypad-doctor` import): `pgType`, `default: { sql }` and the `expression` of a check are SQL that the validation does not check, written as they are into the SQL `lilypad-doctor` prints (the library never runs it).
- The caches and the gate implement `[Symbol.asyncDispose]` (`dispose()` / `close()`).

## Platform capabilities

`src/platform/LilypadPlatform.ts` declares what the library can use from a hosting platform, without depending on any: `background` (keep the instance alive for a promise: `waitUntil`/`after`), `afterResponse` (run work after the response), `shared` (a `LilypadSharedStore`: `get`/`set` with `ttl` in **seconds**/`delete`, a subset of the Vercel Runtime Cache) and `onInvalidate`. Never import `next/*` or `@vercel/*` in the library: `docs/nextjs-vercel.md` shows the adapter the application writes.

- `runInBackground` and `runAfterResponse` always attach an error handler (wrapped by `safeHandler`, so that a throwing `onError` cannot become an unhandled rejection), and fall back to running the work at once if the platform function throws (e.g. `after` outside a request); `runAfterResponse` runs the work once in all, even if `afterResponse` scheduled it before throwing. That throw goes to the optional `onPlatformError`, never to `onError` (it is not an error of the task); the caches log it as a warning (`logPlatformError`).
- `sharedStoreOperation` bounds every shared store call with a timeout; a failure resolves to a fallback. The shared store is never required to answer.

## Logger

- `LilypadLogger<T>` creates one method per channel name in `components` at runtime (for example `logger.info(...)`). `T` is inferred from the keys of `components` only (`LilypadLoggerComponent<NoInfer<T>>`: a `new LilypadConsoleLogger()`, a component of `string`, would otherwise widen it to `string`, which is no `LilypadLibLogger`); its default, `'error' | 'warn' | 'info' | 'debug'`, applies only when nothing is inferred. `dispose()` flushes, then releases the singleton entry (the logger holds no resources: it keeps working). Channel methods return **`void`**: they send in the background, never throw, and `flush()` awaits the messages pending when it is called, not those logged later (tests call `logger.info(...)` then `await logger.flush()`).
- `LilypadLoggerType<T>` is the class type intersected with those channel methods. Use it as the type for logger instances; do not use `LilypadLogger<T>` for this.
- Channel names that clash with a property of the logger (`components`, `register`, `flush`, `dispose`, `name`, `then`, `constructor`, ...) are rejected.
- Output sinks extend `LilypadLoggerComponent` and implement `write(record)` (the only extension point; `formatRecord(record)` gives the text line). See `logger/components/`.
- Every other module takes an optional logger typed `LilypadLibLogger` (`src/logger/LilypadLibLogger.ts`): any object with some of the methods `error`, `warn`, `info`, `debug`, called as `(message, meta)` with `LilypadLogMeta = { source, error?, detail? }` (a `LilypadLogger` and `console` work as they are; pino through `lilypadPinoLogger(pino)`, which passes `{ source, err, detail }` first and reads pino's methods at each call, since pino changes its level by replacing them). Modules log only through `libLog(this.logger, level, source, message, detail?)` (an `Error` detail goes to `meta.error`, anything else to `meta.detail`), which skips missing levels and swallows throws and rejections. The source is the `name` of the instance (the class name before an instance exists). The caches log through `engine.log(level, message, detail)`.
- `src/logger/formatLogValue.ts` has **one walker** (`walk`, cycles through the ancestors only, redaction, throwing getters, depth; a part that cannot be read, such as a `toJSON` or an iterator that throws, becomes `[Unformattable value]` without losing the rest) that builds a small tree, and two renderers: `formatLogValue(value, redaction)` (text, close to `util.inspect`: errors keep stack, own properties and `cause`, and an `AggregateError` its `errors`; nested strings and keys are quoted, with backslashes, line breaks and control characters escaped as in JSON; abbreviated beyond depth 4, and beyond 100 items per array, set, map or object as `… N more items`) and `toLogJson(value, redaction)` (the JSON-safe copy: follows `toJSON` and redacts what it returns, errors as `{ name, message, stack, ...own properties, cause }` (and `errors` for an `AggregateError`), BigInts as `10n`; depth 64, every item). The text form reads a typed array (a `Buffer`) by index, like an array (`Uint8Array(3) [ 1, 2, 3 ]`): listing the keys of a large one takes seconds. The `name`, `message` and `stack` of an error are read by `lilypadErrorSummary` (also used for `record.errors`), and its `cause` and `errors` like the other properties: a field that is not a string is converted with `String()`, and one that throws loses only itself, never the message. Both walk at most 10,000 objects per value (`MAX_WALKED_OBJECTS`, then `[…]`): an object referenced twice is walked twice, so without the budget a value whose levels share their children doubles the work at each level. Neither ever throws. The logger option `redact` (default `LILYPAD_DEFAULT_REDACTED_KEYS`, `false` for none) replaces the values of those keys with `[Redacted]` at any depth, in the message and in `record.context` (`toLogJson(context)`, always an object: anything else is kept under `context`); keys are compared ignoring case, `-` and `_`; `record.parts` stay raw. `safeJson` is `JSON.stringify(toLogJson(value, no redaction))`.
- `platform.background` receives every message being sent. `context()` is read synchronously when the message is logged.
- `@typescript-eslint/no-floating-promises` is an error, because an unhandled rejection terminates the Node.js process. The sending of a message must never reject: component errors (collected with `allSettled`) go to `errorLogging` (sync or async), and if `errorLogging` fails the logger falls back to `console.error`. The messages logged synchronously by `errorLogging` (collected in `#reports` while it runs) report their own failures to `console.error` only: an `errorLogging` that logs on the same logger would otherwise loop through a failing component, in microtasks only, starving the event loop. The report waits for them, so `flush()`, which reads `_pending` once, waits for them too.
- `LilypadDiscordLogger` validates its numeric options, queues messages and batches them (`minRequestInterval`). Its intervals are measured on `performance.now()`. It retries a 429 response after `retry-after` (not beyond 30 s: then the batch fails, and the next batches fail without a request until that time; when the retries run out within 30 s, the next batch waits for `retry-after`). Messages are truncated to 2000 characters without splitting a surrogate pair. A failed batch rejects one message only (an error counting the lost messages, not the notice of the dropped ones, with `cause`), so `errorLogging` gets one error per batch. The queue holds at most `maxQueueSize` messages: the oldest are dropped (resolved, not rejected) and announced in the next batch.

## Flow control

`LilypadFlowControl` is **not generic**: `executeFn<T>`, `singleFlight<T>`, `executeWithTimeout<R>` and `executeWithRetries<T>` are typed per call, so one instance runs executions of different types. The primitives are separate (`singleFlight(key, fn)`, `rateLimit(key)`, `executeWithTimeout`, `executeWithRetries` with an optional `shouldRetry(error, attempt)`); `executeFn` composes them (`consumerIdentifier` optional, no `errorFn`: callers `.catch`). The rate map holds `performance.now()` times (a monotonic clock: a missing key is not a call at time 0) and is pruned at most once per `rate` once it exceeds 1000 keys; `rate: 0` disables it. `executeFn` validates the per-call `timeout` and `retries` like the constructor's, before the rate limit and the first attempt (an invalid one neither uses the rate limit of the key nor is retried), and also for a call that joins one in flight: its options are ignored, but an invalid one still rejects it, so that a programming error fails whether or not a call is running; and the default backoff is capped at 30 s. Single-flight relies on no `await` between the lookup and the registration of the promise (so `rateLimit` stays synchronous). The constructor checks its numeric options.

## How the modules depend on each other

```
LilypadCache ───has──┐                            (bulk sync: LilypadCache only)
                     ├──> LilypadCacheEngine ──uses──> LilypadReadFlights (fetches in flight),
LilypadDbCache ─has──┘    (internal, hooks)            LilypadFlowControl (timeouts), LilypadSharedLevel (L2)
      ├──uses──> LilypadDbMembers, LilypadOwnWrites, LilypadEagerRefresh (dbCache/)
      ├──uses──> a sync strategy (dbCache/sync/): LilypadListenSync | LilypadChangelogSync | lilypadNoSync
      ├──reads──> a table definition of a config (dbConfig/)
      └──uses──> LilypadDbGate (postgres.js, LISTEN/NOTIFY, heartbeat) ──table(definition)──> LilypadDbTable (CRUD)
```

- **LilypadCacheEngine** (`src/cache/LilypadCacheEngine.ts`, types in `LilypadCacheTypes.ts`) is the engine: an in-memory, TTL-based cache with `string | number` keys (`LilypadCacheKey`). It is **internal** (never exported by an entry): its methods are public, check nothing about disposal (they only ignore writes once disposed), and the caches hold one in a private `engine` field. **LilypadCache** (`LilypadCache.ts`) exposes the reads and the writes (`get`, `peek`, `set`, `bulkSet`, `getOrSet`, `getOrSetDetailed`, `getMany`, `entries`, `getAll`, `bulkSync`, `invalidateBulkSync`, `invalidate`, `delete`, `clear`, `purgeExpired`, protected keys, `dispose`), each after `assertNotDisposed`; **LilypadDbCache** exposes no write, so that its values always come from its table. The engine tells its owner what happens through the hooks given to its constructor: `onValueStored(entry)` (each new value, not for `expire`; it must not write), `onEntriesIncomplete()` (eviction, `clear`, the `delete` of a fresh entry, `expireEverything`), `hasReadInFlight(normalizedKey)` (the reads of the owner, for the fences: `LilypadCache` counts every key while a bulk sync waits for its data) and `maxSharedAge()` (the longest an L2 copy lives after its `fetchedAt`, whatever the TTL and stale window of the read: `LilypadDbCache` gives the changelog `lookback`). Tests reach internals as `cache['engine'].store`.
  - Return values: `undefined` means not cached (or expired), and `null` means cached as "does not exist". Keep this distinction.
  - Options: `ttl`, `errorTtl`, `fetchTimeout`, `bulkSync: { fn, ttl, timeout }` (read by `LilypadCache`, and without `fn` by `LilypadDbCache`, not by the engine), `staleWhileRevalidate`, `failureCooldown`, `maxEntries`, `cleanupOnAccessEvery`, `autoCleanupInterval`, `shared`, `platform`, `name`, `tagPrefix`, `logger`. All numeric ones are checked by the constructors, and so are the per-call ones (`set`'s `ttl` and `getOrSet`'s `ttl` and `onError.ttl`: finite, a TTL of 0 or less stores an expired value; `getOrSet`'s `staleWhileRevalidate`: non-negative; its `timeout`: a positive delay of at most 2^31 - 1 ms).
  - `getOrSetDetailed` deduplicates concurrent fetches with `fetches`, a `LilypadReadFlights` (`src/cache/LilypadReadFlights.ts`): a caller joins a fetch of the key only if its ticket is above `currentTicket(key)`, that is if it started after the last change of the key (an invalidation, a change of the sync, a newer write); otherwise it starts a new fetch, and the superseded one stays counted by `fetches.has` (`hasReadInFlight`) until it settles, so that the fences keep discarding it. Never join a read without this check: it would return the value read before the change. The fetch logs a failure and records it for the cooldown, once. Only the fetch is shared: the error fallback (`fallbackResult`, driven by the read option `onError: { fallback: 'stale' | fn, ttl }`) runs for each caller, and is cached only if the key did not change since the call started (the ticket `attempt`, through `setIfNewer`): the fallback of a fetch started before an invalidation never replaces a newer fetch. A different fresh entry written during the fetch (entries are replaced on each write: compared with the entry seen before) is returned as an `L1-HIT` instead of a fallback. The fallback function receives `{ key, error, stale }` and returns `undefined` to rethrow. A fallback that is the stale value keeps its `fetchedAt`. A value resolved after the flow control timeout is not cached. `delete`, `clear` and evictions do not supersede a read in flight: the fence keeps the ticket of the removed entry.
  - **Write ordering**: every entry carries a `ticket`. An async read calls `beginRead()` when it starts, and stores its result with `read.store` (`setIfNewer`, this instance only) or `read.storeFetched` (also L2, ends the cooldown), which discard the result if a write that started later has already been stored. `setIfNewer` and `storeFetched` are private: every new async read path must go through `beginRead()`. A plain write (`set` → `writeLocal`) takes a new ticket. `extendExpiration(key, time)` extends an entry without a new ticket (the renewal of `LilypadDbCache`). A completed load of the whole source (`replaceEntries`) raises `ticketFloor`, so that older reads of missing keys are discarded too. Per-key `fences` play the same role for a key without an entry while a read of it is in flight (`hasReadInFlight`, extended by the owner's hook): expiring a key with no entry sets one, and **removing an entry** (`dropEntry`: `delete`, `clear`, purge, eviction, `replaceEntries`, `removeExpired`) keeps the entry's ticket as one. Every removal must go through `removeEntry`/`dropEntry`, never `store.delete` directly. The bookkeeping (`failures`, `refreshing`, `fences`, `invalidatedMissing`) is pruned by `purgeExpired` and, since that may never run, by `sweepBookkeepingIfLarge` each time one of them has doubled (from 1000).
  - The **bulk sync** is `LilypadCache`'s: its own flow control (`bulkSync.timeout`) and TTL (`bulkSync.ttl`), `bulkSyncFn` from `bulkSync.fn`, and the engine's `replaceEntries(read, data)` (which `LilypadDbCache` calls from its own table load). Without a function it resolves to `false` (rejects with `throwOnError`) and logs nothing. It resolves to a boolean. Its errors are logged and swallowed, unless `throwOnError` is set. Concurrent calls share a sync through `bulkSyncs` (a `LilypadReadFlights`), but only one started after the last forced sync (`bulkSyncInvalidationTicket`): a later call starts another, which may run while the older one ends. While a sync waits for its data (until its timeout at most), every key counts as read (`hasReadInFlight`), so that a key without an entry expired meanwhile gets a fence that discards the value the sync read before. To force a sync, call `forceNextBulkSync()` (public as `invalidateBulkSync()`) instead of writing `bulkSyncExpirationTime`: it also stops a sync that is already running from marking itself fresh, or from being joined. `entries()` leaves out expired or removed entries, so anything that expires or removes a synced entry while the bulk sync is fresh must force the next one: the hooks do it for `clear`, `maxEntries` evictions, the `delete` of a fresh entry and a value that expires before the bulk sync; `invalidate` does it unless `{ invalidateBulkSync: false }`. The bulk sync never stays fresh longer than `ttl`, the lifetime of its entries, nor beyond the expiration of the entries written while it ran (newer than its data, they are kept as they are).
  - `get()` does not remove expired entries by default: the expired value is the fallback for `onError: { fallback: 'stale' }`.
  - The store and the protected keys are keyed by `normalizeKey(key)`, the string form of the key. Each entry keeps the original key, which `entries()` returns. Internal iterations work on normalized keys (`removeEntry`, `expireNormalized`), over a **copy** of the store. With `maxEntries`, the LRU order is `evictionOrder` (a `Set` of the unprotected stored keys, least recently used first, updated by `markUsed`, `dropEntry` and the protected-key methods), so evictions never scan protected keys.
  - A disposed engine ignores every write (`writeEntry` returns `undefined`, and L2 is written only for stored entries), so that fetches still in flight cannot fill it again; it records no failure (a fetch cut short by a shutdown would put the other instances in cooldown), starts no refresh scheduled before (nor fetches if disposed while its refresh took the L2 lock), and `getOrSetDetailed` throws a `LilypadDisposedError` when disposed during its L2 read, and **every public method of the caches throws** a `LilypadDisposedError` (`assertNotDisposed`), except `dispose()`, which returns a promise in every class and is idempotent (`LilypadDbCache` returns the same promise to concurrent calls).
  - `getOrSet` is a wrapper of `getOrSetDetailed`, which returns `{ value, status, refreshFailed }`. A fresh `fallback` entry is returned with `refreshFailed: true`, and with `failureCooldown` it is refreshed in the background once the cooldown is over (`freshHit`). Lookup order: L1 (memory) → L2 (`shared`, with `name` required) → stale value within `staleWhileRevalidate` (never an invalidated one, whatever the window; refreshed via `runAfterResponse`, one per key; a refresh that never starts stops blocking after 60 s; with `refreshLockTtl`, `acquireLock` reads the L2 lock again when the refresh starts, possibly after the response, and skips it when another instance holds it) → fetch. During `failureCooldown`, the fetch is skipped and `fallbackResult` runs with a `LilypadCacheCooldownError`; a local failure time in the future (the wall clock stepped back) counts as now.
  - Entries carry `fetchedAt` (age for L2 adoption), `expirationTime` and `origin` (`source`: a fetch or a write; `fallback`: `fallbackResult`; `shared`: adopted from L2). `expire` sets `expirationTime` to `0` and `invalidatedAt`: an invalidated entry is never served stale, but stays a fallback for `onError`, and `adoptShared` refuses L2 copies fetched before `invalidatedAt` (their removal may have failed or be under way). A key without an entry keeps that mark in `invalidatedMissing` (set by `deleteShared`, and by `dropEntry` for an entry carrying the mark: an invalidated one, or one written after the invalidation, e.g. purged; with a shared level only), for `invalidationMemory` (TTL + fetch timeout + stale window, the defaults: a copy kept longer, by a per-call TTL or stale window or by another instance with a longer TTL, is not covered); an entry written after the mark keeps it as `invalidatedAt`, always for a value produced before it (a stale fallback), and for a newer value while the mark is within `invalidationMemory`, since a value written to this instance only (a bulk sync, a load) does not replace the old copy in L2. `LilypadSharedLevel` ignores envelopes whose `fetchedAt`/`expiresAt` are not finite or whose `value` is `undefined`, and a `failedAt` that is not finite; a `failedAt` in the future counts as now.
  - `expireEverything()` expires every entry and raises `ticketFloor`, discarding the reads in flight; `rejectSharedBefore(time)` stops adopting older L2 values.
  - **L2** is `LilypadSharedLevel` (`src/cache/LilypadSharedLevel.ts`): keys `lilypad:2:<enc(name)>:<kind>:<enc(key)>` with kind `v` (value), `f` (failedAt), `l` (lock), URI-encoded so that no key collides with another; envelope `{ lilypad: 2, value, fetchedAt, expiresAt }`; `lilypadCacheTags` builds the tags (`<tagPrefix>:<enc(name)>`, `...:<enc(key)>`). Bump the format version if it changes. L2 writes: `set` (public `set`/`bulkSet`, and the writes of `LilypadDbCache`) and `storeFetched` (fetches) write L2; fallbacks and loads of the whole source do not. A fetched value is kept in L2 through the larger of the cache's and the read's `staleWhileRevalidate`. The codec runs inside the L2 operations: an `encode` or `decode` that throws is a warning and a miss, never a failed read or fetch. A write does not read L2 first unless `shared.checkBeforeWrite` (which replaces an entry stamped in the future). `decode` ignores an entry whose `fetchedAt` is in the future (a clock ahead, or a planted entry): it would pass every invalidation made before its stamp. `delete` and `invalidate` (via `markInvalid`) remove from L2; `clear`/`dispose` do not.
  - `emitInvalidation(source, keys)` calls `platform.onInvalidate` in the background; `invalidate` emits `manual`.
  - Protected keys are not removed by `delete`/`clear`/purge unless you pass `force`.
  - `expire(key)` is the data part of `invalidate` (without the L2 removal, the bulk sync and the event); `markInvalid` adds the L2 removal. `invalidate` is synchronous in every class.
- **LilypadDbCache** (`src/dbCache/LilypadDbCache.ts`) is a cache on the engine backed by one table of a config (`LilypadDbTableDefinition<V, PK>`), read and written through `gate.table(definition)`. Generics `<V, PK>`; its keys are `LilypadDbKey<V, PK> = V[PK] & LilypadCacheKey`. Public: `get` and `peek` (with renewal), `getOrFetch`/`getOrFetchDetailed`, `getAll` and `getManyOrFetch(keys)` (a `Map` keyed by primary key), `refresh`, `invalidate`, `delete`, `clear`, `purgeExpired`, protected keys, `sqlCreate`/`sqlUpdate`/`sqlDelete`, `dispose`. Options: the cache options without `bulkSync.fn`, plus `gate`, `table` (a definition or a key), `config?`, and `sync` (`LilypadDbCacheSyncOverrides`: `maxAge`, `connect`, `applyChanges`, `onNotification`, `pollInterval`, `poll`, merged over the `sync` of the definition; the strategy, `maxGap` and `lookback` stay the config's). The schema of the table (to filter notifications), the channel and the changelog table come from the definition.
  - `loadTable` is single-flight (`tableLoad`, bounded by `bulkSync.timeout` through its own `loadFlowControl`); `loadRows` loads the whole table (with the timeout signal), calls `replaceEntries`, and replaces `members`, a `LilypadDbMembers` (`src/dbCache/`): the keys of the rows of the table, each with a ticket. Once a load completed, and while one runs (`beginLoad`/`endLoad`: a row inserted during the first load is newer than it), the `onValueStored` hook (`members.follow`: non-fallback values, row → member, `null` → removed), `members.add` (INSERT/UPDATE of a key not cached) and `members.forget` (truncate, bulk change) keep them up to date; `purge`, eviction and `clear` do not touch them. The members noted by `add` and not yet verified (by a load or a stored value) are bounded: beyond a quarter of the table and at least 1000 (a flood of forged notifications), `add` forgets the members, and the next `getAll` loads the table (never while a load runs, which it would void: the next `add` after it checks again). While a load waits for its rows (`loadsReading`, not while it stores them, so that its evictions leave no fence), every key counts as read (`hasReadInFlight`): a change of a key held by nothing else (`isHeld`, which leaves the load out) is not re-read but expired (`forgetUnheld` → `markInvalid`), whose fence discards the loaded row, and `loadRows` leaves out of the rows it returns those whose `currentTicket` exceeds its ticket. A load voided by a change of the whole table while it ran (`members.forget` without `empty`, or, during the first load, any `forget`: `members.known` is false after it) returns every row it read, with `complete: false`: `getAll` loads again (`loadTableForCall`: the voided load may have started before the call), and answers with the rows of a second voided load as read, since it started during the call.
  - `getAll()` loads the table when `members.isLoaded(trustedSince, bulkSync.ttl)` is false (never loaded, loaded before the sync became trusted, even within `bulkSync.ttl`, or, while no sync is trusted, after `bulkSync.ttl`), then fetches the stale or missing members with `selectByPrimaryKeys` (`fetchRows`, L1 only), or reloads if they exceed 25% of the members (`LILYPAD_FULL_LOAD_RATIO`) and the call did not load already. When that fetch fails, and the call did not load, did not time out, and the gate is not closed nor the cache disposed (a `LilypadDisposedError`), it loads the table instead, once: a member noted from a notification may hold an id that the database rejects (text for an integer key), and only a load, which reads no member by key, replaces it. `getManyOrFetch(keys)` fetches only those keys (each once, keyed as first given). The result (`rowsOf`) is built from the store **and** from the rows the load (`loadTable` returns them) and `fetchRows` just read, since `maxEntries` may have evicted them. `fetchRows` shares a query per key (`rowFetches`, a `LilypadReadFlights`: only a query that started after the last change of the key); `queryRows` takes the `read` begun by its caller.
  - **Sync strategies** (`src/dbCache/sync/`): the cache builds one `LilypadDbSyncStrategy` (`start`, `beforeRead`, `trustedSince`, `seesOwnWrites`, `dispose`) and gives it a `LilypadDbSyncHost` (closures over `applyChange`, `applyTruncate`, `applyBulkChange`, `expireEverything`, `emitInvalidation`, `forgetOwnWritesCoveredBy`, ...). `listen` → `LilypadListenSync` (default; `connect: 'lazy'` defers LISTEN to the first read; `onNotification` is called after the change is applied, `applyChanges: false` leaves the cache to it), `changelog` → `LilypadChangelogSync`, `none` → `lilypadNoSync`. `beforeRead()` returns `undefined` when there is nothing to wait for, and the reads await it **inline** (`const syncing = ...; if (syncing) await syncing;`), so that they stay synchronous up to the fetch registration: never wrap it in an `async` helper. Failed changelog reads and lazy LISTEN back off (`LilypadBackoff`). There is no runtime schema check (no `verify`).
  - **Trust and renewal**: `sync.trustedSince()` is when `LISTEN` became active (reset on reconnect; `undefined` while `gate.isListenHealthy()` is false, or if `applyChanges: false`) or when the changelog chain started (`readAt`, on the wall clock like `fetchedAt`; `undefined` beyond `maxGap` after the last applied read, measured on `performance.now()`, and when no read was applied within `pollInterval`, two with `poll: 'background'`, measured on `performance.now()` from the end of the apply: `get` never reads the changelog, and a read may fail). `renew()` extends an entry past its TTL (`extendExpiration`), without a query, if its `origin` is `source`, it is not invalidated (`expirationTime > 0`), `fetchedAt >= trustedSince` and it is younger than `sync.maxAge`. `get`, `peek`, `getOrFetchDetailed` and `getAll` renew before reading. L2 lifetimes are never extended.
  - `refresh(key)` re-fetches the row (`fetchRow`, with `fetchTimeout`). Calls are coalesced per key (`refreshes`): one running query, plus at most one queued after it for the calls made meanwhile (rejected with a `LilypadDisposedError`, with no query, if the cache was disposed before it starts).
  - `sqlCreate`/`sqlUpdate`/`sqlDelete` write through to the database with the table handle (which returns the `xid`), then cache the row returned by the database, so generated primary keys work. `writing(key, write)` counts the write in `writesInFlight` (when the key is known before it: not a generated primary key), which `hasReadInFlight` includes, and takes the start ticket: a change of the key applied during the write leaves an entry or a fence newer than it, even if the key is not held. `storeWritten`, called inside `writing`: if `currentTicket(key)` exceeds the start ticket, it expires the key instead of caching the row; if the cache was disposed meanwhile, it does nothing. Otherwise it caches with `engine.set` (a new ticket, so reads started before lose) and, if `sync.seesOwnWrites` (not `listen` with `applyChanges: false`), records the write in `ownWrites`, a `LilypadOwnWrites` (`src/dbCache/`: 10 minutes on `performance.now()`, at most 32 transactions per key); a change with that `xid` is skipped (`ownWrites.consume`) while the entry still holds the last own write. Deletions are cached as `null`, which also applies to protected keys; `sqlDelete` resolves to whether a row was deleted. `sqlCreate` returns, uncached and with a warning, a row the `select` hook returns without its primary key.
  - **Changes**: `applyChange(op, id, mode, xid)`. `applyTruncate(mode)` and `applyBulkChange` go through `forgetTable(empty)`; a bulk change (a `BULK` notification, or a changelog read with more than `LILYPAD_BULK_CHANGE_THRESHOLD` = 1000 rows) is an eager truncate without the L2 removal of each key. The changelog sync reduces a read with `lilypadNetChanges` (the last change of each row after the last `TRUNCATE`) and emits one event with each key once. Eager re-reads have a budget of 1000 keys per second per cache (`LilypadEagerRefresh`, on `performance.now()`; a key already in the batch being gathered is not charged): beyond it, a notified key is only `markInvalid`. Before that, `LilypadListenSync` bounds the notifications themselves (`takeBudget`, on `performance.now()`): 2000 per second per cache, and one `TRUNCATE`/`BULK`; beyond, `overflow` applies one change of the whole table (`applyBulkChange` and a `wholeCache` event) at once, and once more at the end of the second (an `unref`ed timer, cleared by `dispose`) for the notifications left, whatever their number. The router logs a malformed notification at most once a minute (`warnMalformed`). The primary key counts as numeric (`numericPrimaryKey`) when `cols[pk].type` is `'number'` or once a stored row has a numeric key. Changelog changes are `lazy` (trusted: only the triggers write the changelog): a DELETE of a held key caches `null` (of a key not held: no entry, only `members` and L2 are cleared, so mass deletes do not evict), an INSERT/UPDATE of a held key is `markInvalid` (whose fence discards a read in flight without a query). Notifications are `eager` and **untrusted** (any role can `NOTIFY`): a change of a held key, DELETE included, re-reads the row (`eagerRefresh`, a `LilypadEagerRefresh` in `src/dbCache/`: the keys notified in the same microtask are re-read with one `selectByPrimaryKeys` by `rereadNotified`, through `queryRows(keys, read, true)`, which stores with `storeFetched`; a failed batch expires its keys; `eagerRefresh.has` counts them for `hasReadInFlight`); a DELETE of a key not held caches nothing (`getAll` re-reads its member); a TRUNCATE notification (`applyTruncate('eager')`) marks the table as not loaded instead of empty. Every INSERT/UPDATE calls `members.add`. `TRUNCATE` from the changelog (statement trigger, `row_id` NULL) empties the members with no query. A failed `apply` of the changelog keeps the cursor and backs off.
  - **Changelog** (`src/dbGate/LilypadChangelog.ts`): triggers write `(xid, table_schema, table_name, row_id, op)` rows. One statement trigger per event with transition tables (`lilypad_old`/`lilypad_new`, `LILYPAD_CHANGELOG_OLD_ROWS`/`NEW_ROWS`) records all the rows of a statement with one `EXECUTE`d `INSERT ... SELECT` that reads only the primary key. The function no longer serves the row triggers of version 3 and earlier: called by one, it raises a `WARNING` and returns (the write goes on unrecorded; the schema check reports `missing-changelog-trigger`). Rows with a NULL `row_id` that are not a TRUNCATE are skipped by the reader, and so are the rows without a schema (version 1). `readLilypadChangesBatch` returns, for each request, the rows of the transactions the previous read could not see: the cursor is `LilypadChangelogCursor = { xmax, xip }` (`pg_snapshot_xmax` / `pg_snapshot_xip` of the read's snapshot) and the next read asks for `xid >= xmax OR xid = ANY(xip)`. Each change is returned by exactly one cursor read, whatever the commit order and however long a transaction runs, so there is no dedup of applied changes. `lilypadCursorCovers(cursor, xid)` prunes `ownWrites`. `readLilypadChanges` is the one-table wrapper. The caches of a gate subscribe to one `LilypadChangelogReader` per changelog table (`src/dbGate/LilypadChangelogReader.ts`, a `WeakMap` keyed by gate), which reads every subscribed table in one query and calls each cache's `apply` with its own request (cursor or lookback). Without a trusted cursor (first read, or more than `maxGap` since the last one) it reads a time `lookback` and expires every entry. Notifications carry `xid` and `schema`, and the reader resolves the table with `to_regclass`. The trigger function carries its version in its comment (`LILYPAD_CHANGELOG_VERSION`, 9: bump it for any change of the SQL it versions). Since version 7 it runs as its owner: a `DO` block (`recordDoBody`) creates it `SECURITY DEFINER SET search_path = pg_catalog, pg_temp`, turning the placeholders of its body (`__lilypad_changelog__`, `__lilypad_changelog_literal__`, `__lilypad_prune__`) into the arguments of one `format()` (nested `replace()` calls would read again the names they insert, which may contain a placeholder; the channel may not): the changelog table and the prune function qualified with the schemas it resolves (no other schema on the path: an overload in a schema writable by others, e.g. `public.to_jsonb(integer)`, would win over the polymorphic built-in and run as the owner; the `UPDATE` branch compares the keys with `to_jsonb(...) =` for the same reason), and the SQL revokes `INSERT, UPDATE, DELETE, TRUNCATE` on the changelog and `EXECUTE` on the record and prune functions from `PUBLIC`: the caches trust every changelog row, so no role but the owner may write one. The function reads only the primary key, and `to_jsonb` of a non-built-in value runs its cast to `json` if one exists, else its output function, and recurses into the elements of an array and the fields of a composite (not the `search_path`), so a key whose cast or I/O function a role owns would run that role's code as the owner. Version 9 **fails closed**: before it evaluates the key, it refuses to record unless the key column exists (an `attnum > 0`, not-dropped column named `TG_ARGV[0]::pg_catalog.name`, clipped as the `%I` is) and its type is proven safe. The safety rule is one SQL fragment (`lilypadSafeKeyTypeSql`) that the trigger and the schema check share, so they cannot drift. It walks the type, resolving domains to their base and registered array types to their element (bounded depth, fail closed beyond it), and requires every other node to be safe: a built-in type (OID below `LILYPAD_FIRST_NORMAL_OBJECT_ID`, 16384), or a base (`typtype` `b`) or enum (`e`) type whose **type, its output function and any `json`/`jsonb` cast function are owned by superusers (or built in)** — ownership of the type alone is not enough, because a superuser-owned type can keep an older cast, or carry a cast `WITH FUNCTION` a role owns, and that role could then replace the function. A user-defined (non-built-in) composite, range or multirange type is refused (built-in ones, such as `int4range`, are accepted). This keeps the types of a superuser-installed extension (e.g. `citext`, whose type and functions are superuser-owned) working, while refusing a type a non-superuser controls. It is the one value of a cached table the function evaluates; the schema check applies the same fragment and reports such a key (`unsupported-key-type`), or a missing key column (`missing-column`), on a `changelog` table and on a `listen` table that the changelog triggers notify (or that the fix of its notifications gives them): their writes go through the same guard. For an install older than version 9, the message says to change the key before installing version 9 (which fails every write of the table). While any table whose key the triggers read has an unsafe type or a missing key column (`blockedTables`), every fix of the changelog machinery is withheld, for every table (no `fix`, and one sentence naming the blocked tables in the message): the changelog SQL, the changelog trigger and notify fixes, the `writable-changelog` `REVOKE`, and the pruning fixes but the one-off `DELETE` of `unpruned-changelog`; a missing table keeps its `CREATE TABLE`, without its triggers. The problems that carry such a fix are registered with `touchesChangelog` as they are built. The same fixes are withheld while the installed function is of a version above `LILYPAD_CHANGELOG_VERSION` (the warning `newer-changelog`, whatever the strategies of the config: the notify fixes install the changelog SQL too): they would install the older SQL of this library under the services of a newer one that share the database (both reasons can hold: one sentence names them). What remains trusted: the owners of the changelog and of its functions, and the superusers who own a key's type and its cast and I/O functions. The reader ignores the rows whose `xid` is at or above the `xmax` of its snapshot (`next_xmax` of `targets`): no trigger writes them, and a cursor read would return them again at every read. The names derived from a table name (`<prefix>_lilypad_insert`...) are cut to 63 bytes with a hash of the prefix (`derivedName`), so that PostgreSQL never truncates them into one; `lilypadChangelogTriggerSql` also drops the unshortened names of version 5, which PostgreSQL truncates the same way. The functions and indexes named after the changelog table (`changelogObjectName`) keep the names PostgreSQL truncates while the prefix is under 62 bytes (they stay distinct, as earlier versions installed them), and are cut with a hash from 62 bytes, where PostgreSQL would merge them (the record function dropped by the `DROP FUNCTION` of the prune one, the `changed_at` index never created); the SQL then drops the one index that earlier versions created under the truncated name. The default pg_cron job name stays `<prefix>_prune`, never shortened (a job name is not an identifier). `lilypadChangelogSql` and `addListener` check the channel (`assertLilypadChannel`: non-empty, at most 63 bytes). The bodies are dollar-quoted with a tag they do not contain (`dollarQuote`: a name may contain `$`). An installed version below `LILYPAD_CHANGELOG_VERSION` (or a function without a valid version comment) is the error `outdated-changelog`, whose fix is the changelog SQL of this version: the generated SQL keeps the statements that upgrade every older install (they do nothing on a current one), and a bump only appends to them; a version above it is the warning `newer-changelog`. The statement branch inserts the changes, reads `GET DIAGNOSTICS ... ROW_COUNT`, and notifies one `BULK` above `notifyBulkThreshold` (default 1000), else each row (the transition table is read again). Pruning (all three throw for an `olderThan` below `LILYPAD_MIN_CHANGELOG_RETENTION`, one hour, unless `force`, `prune.force` for the trigger; the schema check passes it to keep an installed retention in its fixes): `pruneLilypadChangelog` (from the app: in batches of `batchSize`), `lilypadChangelogPruneScheduleSql` (a pg_cron job), or the `prune` option of `lilypadChangelogSql`: the trigger calls a `SECURITY DEFINER` `<changelog>_prune()` function on about one statement in `every`, only in `READ COMMITTED`. A `DO` block creates it with the changelog table qualified with its schema and `SET search_path = pg_catalog, pg_temp`: without `pg_temp` listed last, it is searched first, and any role could make the function delete from a temporary table whose triggers run as the owner. The options are recorded in a `lilypad-prune:` comment of the trigger function, which the schema check reads back (`installedLilypadChangelogPrune`) so that its fixes keep them.
  - **Schema check** (`src/dbGate/`, run only by `lilypad-doctor`/`runLilypadDoctor`/`checkLilypadSchema`, never by the caches): `LilypadSchemaTypes.ts` has the types they share (the options, the problems, the result, `LilypadSchemaTableShape`), `LilypadSchemaFacts.ts` reads the catalogs only (`readLilypadSchemaFacts` = `readDatabaseFacts` + `readTableFacts`, every table in one query, with the columns, constraints and indexes of the tables that have a `shape`; the trigger arguments decoded from `encode(tgargs, 'escape')`, which escapes the bytes beyond ASCII, by `decodeLilypadTriggerArgs`; for a missing `schema.table`, its `missingSchema` when the schema does not exist either; nothing that throws for a lack of privilege: the existence of `cron.job` is read from `pg_class`, since `to_regclass` throws without USAGE on the schema), `LilypadSchemaPruning.ts` evaluates the pruning (`evaluatePruning`, `suggestPruning`, the parsing of cron commands and intervals), `LilypadSchemaShape.ts` compares a table with its description (`evaluateLilypadTableShape`, pure; `normalizeLilypadPgType`; `lilypadCreateTableSql`), and `LilypadSchemaCheck.ts` has `evaluateLilypadSchema` (pure, unit-tested), `checkLilypadSchema` (both) and the formatting of the problems (`formatLilypadSchemaProblems`, and `formatLilypadSchemaFixSql` for `--sql`, which comments out the fixes whose `fixDatabase` is another database). The options list per-table requirements (`{ table, primaryKey, changelog?, notifyChannel?, shape? }`; `changelog` defaults to whether the changelog is checked, `notifyChannel` to the top-level one); `lilypadSchemaCheckOptions(config)` (`LilypadDoctor.ts`) derives them from a config (the changelog only if a table uses it, `minRetention` = max of `changelog.minRetention` and each table's `maxGap`/`lookback`, `checkPruning: true`; `changelogTable` always, so that with `changelog: false` the fixes of the `listen` tables still install the config's changelog, `readChangelogTarget`). The shape compares structure, never names: columns (`pgType` exact after normalization, else `type` against the category, warning), nullability, defaults (incl. `generatedPrimaryKey`), the primary key, unique keys (any PK/unique constraint/unique non-partial index on the same set), foreign keys (same referenced table and column pairs, then actions), indexes (same columns in order, same method), checks (by name); `strict` warns about the undeclared ones; `undeclared-required-column` always. Missing foreign keys are `deferred`: pushed after every table, before the pruning problems, so that the fix SQL (in problem order) creates tables first. A missing table's fix is `CREATE TABLE` (when every column has a `pgType`; after `CREATE SCHEMA IF NOT EXISTS` when its schema is missing) plus the triggers its sync needs; a generated primary key gets an identity (integer; added to an existing column, followed by a `setval` past the keys of the rows) or `gen_random_uuid()` (`uuid`), and a default it cannot write (`default: true`, a generated key of another type) is left as a comment. Every fix that installs the changelog installs the same SQL: the pruning found or suggested, and one channel (the function notifies on one): `notifyChannel`, else the installed one when no table needs another, else the first table's; a table that needs another channel gets no fix (it needs a trigger of its own), and the fixes of the tables leave the changelog SQL out when a changelog problem carries it. A retention or a `DELETE FROM` target that the pruning parser does not fully understand (an ISO interval, an unknown unit, a command it cannot tokenize) is unknown, never misread, and comments (nested too) are ignored, a dollar-quoted string is a literal (but the body of a `DO` block is code): the retention is read only from the one statement of the command that deletes from the changelog, a `DELETE` with one interval, and only a job whose command is one `DELETE FROM <changelog> WHERE changed_at < <now> - <interval>` gets a fix (scheduled again, any other would lose part of its command). A job's qualified name is compared with the schema the changelog resolves to. The pruning is checked (and its facts read: `cron.job`, the oldest row) unless `changelog.checkPruning` is `false`. Without the pruning check, the fix of a missing or outdated changelog keeps the installed `prune` option. The changelog check requires the enabled (`tgenabled IN ('O','A')`) changelog statement triggers to record INSERT, UPDATE and DELETE together, with the right transition tables (`recordedEvents`; a changelog row trigger records nothing). The `listen` check (`pg_notify` in any case, the channel with its case) requires the notifying triggers to cover the three events (possibly split across triggers; a statement trigger counts only if it is a changelog trigger, a row trigger only if it is not).
  - Problems have a `severity`: `error` (`ok` false, `lilypad-doctor` exits with 1, `report.assertOk()` throws a `LilypadSchemaCheckError`) or `warning`. The pruning checks, `newer-changelog` and `writable-changelog` (a role other than the owner of the changelog granted a write of it, from `aclexplode` of the table and of its columns: `facts.changelog.writers`; its `REVOKE` comes after the changelog SQL in the fixes) report warnings. The pruning checks detect the `prune` option (its comment) and the active `cron.job` jobs of this database that `DELETE FROM` the changelog (`lilypadCommandDeletesFrom`, retention from `lilypadPruneCommandRetention`); a retention `<= minRetention` (default 1 h) is the error `short-changelog-retention`. With nothing detected, `pruning` not `external` and `n_tup_del = 0`, the warning `no-changelog-pruning` carries the best fix (`suggestPruning`: pg_cron when known to run, else the `prune` option, which the missing/outdated changelog fix then includes); `pruning: 'trigger'`/`'cron'` forces one of them (`'cron'` assumes this database when `cron.database_name` is unreadable). `unpruned-changelog` warns when the oldest row is older than the retention (24 h if unknown) plus 7 days. Pruning problems are pushed after the others. The facts of pg_cron and of the oldest row are best effort (`null` when unreadable). `n_tup_del` is flushed asynchronously: the integration tests of the schema check declare `pruning: 'external'` (the `check` helper), and the pruning ones use a changelog table of their own.
  - With the `listen` strategy, it subscribes to the `LilypadNotificationRouter` of its gate (`src/dbCache/sync/LilypadNotificationRouter.ts`, a `WeakMap` keyed by gate and channel), which registers **one** listener on the `notifyChannel` of the config (default **`cache_events`**; `callbackId: 'lilypad_notification_router'`) for every cache of the gate, parses each payload once, and hands it to the subscribers of its table (unqualified name); the last subscriber to leave removes the listener, unless one subscribed again meanwhile. `parseLilypadNotification` validates the JSON payloads `{ table, id, op: 'INSERT'|'UPDATE'|'DELETE'|'TRUNCATE'|'BULK', schema?, xid? }`, where `id` is a string or a number (absent for TRUNCATE and BULK); anything else is ignored, with at most one warning a minute (`warnMalformed`). `resolveNotifiedKey` keeps the type of a known key, or converts a string id to a number when the key is numeric. INSERT and UPDATE re-fetch only the keys that are cached or being fetched; any other key is only added to `members`. On `onReconnect`, `applyBulkChange` (every entry expired, older L2 copies refused, members forgotten) and a `wholeCache` `notification` event. The listener callback and `onReconnect` do nothing once the cache is disposed; `dispose()` awaits a LISTEN still starting before unsubscribing, and a LISTEN that completes after `dispose()` unsubscribes itself. The changelog trigger of `lilypadChangelogSql` sends these payloads (unless `notifyChannel: false`); `LilypadDbGate.integration.test.ts` also contains a minimal custom trigger.
- **LilypadDbGate** wraps postgres.js.
  - The main `sql` client uses `prepare: false`. Keep it that way; it was deliberately removed in a recent commit. The `statementTimeout` option (default 30 s, `false` to leave the database setting) sets Postgres `statement_timeout` on this client: the cache's timeouts do not cancel queries, so this frees the pool. `statementTimeout` and the `pool` durations are at most 2^31 - 1 ms (`0` disables a pool timeout, as in postgres.js), `pool.max` is a positive integer. `close({ timeout })` (default 5 s) is idempotent (same promise), validates its timeout before the gate counts as closed, and makes the table methods and `addListener` throw a `LilypadDisposedError` (`assertOpen`, public so that `LilypadDbTable` calls it).
  - Do not cancel queries with the postgres.js `.cancel()`: in 3.4.x it drops the promise of the cancel request, so a failed cancel connection becomes an unhandled rejection.
  - LISTEN goes through postgres.js `listen()`, which opens its own dedicated connection per client (no pool options needed). The gate listens on `sql`, or on a second client when `listenerConnectionString` differs from `connectionString`.
  - **Heartbeat** (`LilypadListenHeartbeat`, option `listenHeartbeat`, default 15 s, `false` to disable): while channels are listened to, the gate listens on `lilypad_heartbeat_<id>` and sends itself `pg_notify` through the main pool; `isListenHealthy()` is true while a beat came back within 2.5 intervals, measured on the monotonic clock (`performance.now()`); without heartbeat, once LISTEN is active on a channel. The heartbeat timer starts only if `heartbeatStop` still holds its own LISTEN (a stop during the start wins), and a failed start is retried by `isListenHealthy()` after a `LilypadBackoff`. postgres.js gives no signal while the listen connection is down (its internal listen client overrides `onclose`), which is why it exists.
  - Callbacks are grouped by channel and keyed by `callbackId`, so re-adding the same id replaces the old callback. The postgres.js callbacks of a channel act only while its `ChannelListener` is the current one: postgres.js keeps the listener of a failed LISTEN (it gives no `unlisten` for it) and listens to it again on every reconnection, which would otherwise repeat each notification and `onReconnect`. Such a channel is then never `UNLISTEN`ed (postgres.js still counts the failed listener), its notifications ignored. The singleton signature includes the `channel`/`callbackId` of `listen`. Callbacks may be async: their errors are caught and logged. `removeListener` UNLISTENs the channel when its last callback is removed, stops the heartbeat with the last channel, and never rejects. After a reconnection it sends no UNLISTEN: postgres.js listens again with new listener objects, which the `unlisten` it returned does not remove (no public workaround), so the channel stays listened to, its notifications ignored.
  - postgres.js calls `onlisten` on the first LISTEN and again after every reconnection. From the second call on, the gate runs the optional `onReconnect` of each callback.
- **LilypadDbTable** (`src/dbGate/LilypadDbTable.ts`, from `gate.table(definition | key)`, its `definition` public; description types and errors in `src/dbConfig/LilypadDbSchema.ts`, entry `schema`): the CRUD helpers of one table, generic over `LilypadDbTableDefinition<T, PK>` (`PK` defaults to `keyof T`). Queries name the table `qualifiedName` (`sql('public.users')` quotes each part), messages use the unqualified `tableName`: `selectAll({ signal })` (an SQL cursor in a transaction, `DECLARE` then one `FETCH` of 1000 rows per batch, so that `statementTimeout` bounds each batch and not the whole read; it stops, and rolls back, once the signal is aborted), `selectByPrimaryKey`, `selectByPrimaryKeys` (`IN`, one query per 1000 keys, after removing the duplicate keys), `insert`, `update`, `delete`. `generatedPrimaryKey` leaves the primary key out of inserts; an update leaves it out of its `SET`. The column type `bigint` keeps string keys. Rows are mapped to `T` with the `select` hook (`definition.hooks`), or by copying the `cols` keys. Writes go through the `write` hook, whose result **replaces** the data, so it can remove properties. The `cols` metadata is optional; at runtime only the `type` of the primary key is read (by `LilypadDbCache`). `sql` is `readonly` on the gate.
  - Only the `cols` keys are selected and returned (unless there is a `select` hook, which gets `*`) and written: extra properties of the data are dropped on purpose, to prevent mass assignment. `undefined` values are not written. Data with nothing to write throws `LilypadDbEmptyWriteError`, a missing primary key `LilypadDbMissingPrimaryKeyError`.
  - `insert`/`update` return `{ row, xid }` and `delete` returns `{ deleted, xid? }`: they add `pg_current_xact_id()::text AS __lilypad_xid` to `RETURNING` (the same function as the changelog's `xid` default) and strip it before `mapRow` (a table column of that name is missing from the returned rows). `update` throws `LilypadDbNotFoundError` when no row matches.
