#### Upgrading

| Change                                                                                                                                                                                                                                                                                                                                                                                                                                             | What to do                                                                                                             |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **The per-call TTLs of `LilypadCache` must be finite numbers** (`@lilypad-studio/libs/cache`, also `LilypadDbCache` in `@lilypad-studio/libs/db`). `set(key, value, ttl)` throws, and `getOrSet`/`getOrSetDetailed`/`getOrFetch` reject before fetching, with a `RangeError` when `ttl` or `onError.ttl` is `NaN` or `±Infinity`. A `NaN` TTL used to store an entry that never expired. A TTL of 0 or less still stores an already expired value. | Pass a finite number of milliseconds, e.g. `Number.MAX_SAFE_INTEGER` for a value that should practically never expire. |
| **The per-call `staleWhileRevalidate` must be a non-negative finite number**: `getOrSet({ staleWhileRevalidate })` rejects with a `RangeError` otherwise. `Infinity` used to serve invalidated values as `STALE`.                                                                                                                                                                                                                                  | Pass a non-negative finite number of milliseconds.                                                                     |

#### Fixed

- `getOrSet` with `onError`: the fallback of a fetch started before an `invalidate` no longer replaces the value of a newer fetch. The cache used to keep the pre-invalidation value (a `'stale'` fallback) for `errorTtl`, and discard the fresh one.
- Invalidating a key that is already invalidated (`invalidate`, or two quick changes of the same row in `LilypadDbCache`) now discards the fetch of the key started in between. The value that fetch read before the second change used to be cached as fresh for the whole TTL.
- A shared cache no longer picks up the old shared copy of a key that `invalidate` or `delete` removed while the removal from the shared store failed or was still under way, when the key had no local entry or its invalidated entry was purged. `LilypadDbCache` gets the same protection for the keys it does not hold, when a change of their row removes their shared copy.
- A shared entry whose `fetchedAt` or `expiresAt` is not finite, or whose `value` is `undefined` (possible with a store that does not go through JSON), is ignored with a warning, instead of being cached forever. A shared failure time that is not finite is ignored, and one in the future (another instance's clock ahead) counts as now, so that the `failureCooldown` of a key cannot last forever.
- The failure, fence and refresh bookkeeping of a cache stays bounded without `purgeExpired` (no `autoCleanupInterval` or `cleanupOnAccessEvery`): it used to keep every distinct key whose fetch had failed, beyond `maxEntries`. A `STALE` value whose refresh failed now stays reported with `refreshFailed: true` after `purgeExpired`.
- A disposed cache no longer records failed fetches in the shared level (a fetch cut short by a shutdown put the other instances in `failureCooldown`), no longer starts a `staleWhileRevalidate` refresh scheduled before `dispose()`, and a `getOrSet` disposed while it read the shared level rejects with `LilypadDisposedError` instead of fetching.
- With `maxEntries`, invalidating an entry no longer makes it the most recently used one, and `removeProtectedKeys` evicts at once the entries beyond the limit.
