#### Upgrading

| Change                                                                                                                                                                                                                                                                                                                                                                                                                                                              | What to do                                                                                        |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| **`defineLilypadDb` rejects a reference to a table name that several schemas of the config share, none of them the default one** (`@lilypad-studio/libs/schema`). With `archive.orgs` and `audit.orgs` in the config, `references: { table: 'orgs' }` resolved to whichever came first in `tables`: reordering the keys silently changed the foreign key. A name of the default schema still wins, and a name of a single table of the config still resolves to it. | Qualify the reference: `references: { table: 'orgs' }` → `references: { table: 'archive.orgs' }`. |
| **`defineLilypadDb` rejects arrays where the config expects objects** (`@lilypad-studio/libs/schema`): `tables`, a table, `cols` and a column. A JavaScript config with `tables: [orgs, users]` was accepted with the table keys `0` and `1` (and `cols: [...]` with columns named `0`, `1`...).                                                                                                                                                                    | Write them as objects: `tables: [orgs, users]` → `tables: { orgs, users }`.                       |
| **`defineLilypadDb` checks the `type` of a column against more `pgType` spellings** (`@lilypad-studio/libs/schema`): `dec(p,s)`, `char varying(n)` and the arrays written `integer ARRAY`, `integer ARRAY[4]` or `integer[3]` are now known, so a `type` that does not fit them (e.g. `{ type: 'number', pgType: 'dec(10,2)' }`, which postgres.js returns as a string) is rejected, and a missing `type` is now inferred.                                          | Fix the `type`, or leave it out.                                                                  |
| **A bare `bpchar` is no longer read as `character(1)`** by `normalizeLilypadPgType` (`@lilypad-studio/libs/schema`) and `lilypad-doctor`: PostgreSQL writes `bpchar` for a blank-padded column without a length, which is not a `character(1)`. `pgType: 'bpchar'` on a `character(1)` column, or `'char'`/`'character'` on a `bpchar` column, is now a `column-type-mismatch` error.                                                                               | Declare the type the column has: `char`/`character(n)` for a fixed length, `bpchar` for none.     |

#### Fixed

- `lilypad-doctor` no longer reports a false `column-type-mismatch` error for a `pgType` that PostgreSQL writes differently: `numeric(10)` (`numeric(10,0)`), `bit` (`bit(1)`), `text[][]`, `integer ARRAY`, `integer ARRAY[4]` and `integer[3]` (all `integer[]`: PostgreSQL ignores the dimensions of an array), `dec(10,2)` and `char varying(10)`. `normalizeLilypadPgType` (`@lilypad-studio/libs/schema`) now writes them as `format_type` does.
- The type `LilypadDbHooks` (`@lilypad-studio/libs/schema`) accepts `undefined` for the hooks of a table, as `bindLilypadDbHooks` does at runtime (the table is left as it is), under `exactOptionalPropertyTypes`.
- The docs say that a config is trusted code: `pgType`, `default: { sql }` and the `expression` of a check are not checked, and go as they are into the SQL that `lilypad-doctor` prints (the library never runs it).
