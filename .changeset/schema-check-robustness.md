#### Upgrading

| Change                                                                                                                                                                                                                                                                                                                                                                                   | What to do                                                                                                   |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **`lilypad-doctor init --force` no longer writes a second file of a config.** When another file of the same config exists (e.g. `lilypad.config.mjs` next to the `lilypad.config.ts` to create), it now exits with 2 and writes nothing, instead of writing the file and printing a warning: the loader refuses a config with two files. `--force` still overwrites the file it creates. | Remove the other file first, then run `lilypad-doctor init --force` again.                                   |
| **The pg_cron fix to run in another database moved to `fixDatabase`.** The `fix` of a `no-changelog-pruning` problem that schedules the job from the database pg_cron runs in no longer starts with a `-- Run in the database "<name>", where pg_cron runs:` line: that database is its new `fixDatabase` (see Added).                                                                   | Code that ran `problem.fix` wherever it came from: run the fixes that have a `fixDatabase` in that database. |

#### Added

- `LilypadSchemaProblem.fixDatabase` (`@lilypad-studio/libs/db`): the database a `fix` must run in, when it is not the checked one (the pg_cron job scheduled from the database pg_cron runs in). `lilypad-doctor --sql` leaves these fixes out of the migration, as comments under `-- Run in the database "<name>", not in this one:`, and the report shows them under `Run this SQL in the database "<name>":`. Before, `--sql` mixed them into the migration, which then failed at `CREATE EXTENSION pg_cron`.

#### Fixed

- `lilypad-doctor` and `checkLilypadSchema` (`@lilypad-studio/libs/db`) no longer fail with `permission denied for schema cron` when pg_cron is installed and the role of the check has no USAGE on its schema (pg_cron grants it to no role but its owner by default): the jobs are then unknown, as when `cron.job` cannot be read.
- A changelog trigger on a primary key whose name has characters beyond ASCII (e.g. `clé`) or a backslash is no longer reported as `wrong-trigger-primary-key`, which its own fix could not clear.
- The fixes of a config with both `changelog` and `listen` tables install the same changelog SQL: a table's fix no longer reinstalls the changelog without the suggested pruning (which the next check reported again). The changelog function notifies on one channel: a table that needs another one (a per-table `notifyChannel` of `checkLilypadSchema`) gets no fix, and its message says to give it a notifying trigger of its own.
- The `CREATE TABLE` fix of a missing table gives a generated `uuid` primary key (`generatedPrimaryKey`) the default `gen_random_uuid()`, and starts with `CREATE SCHEMA IF NOT EXISTS` when the schema of the table is missing too (the message says so). A default it cannot write (`default: true`, a generated key of another type) is listed as a comment after it, instead of a table that the next check rejects. `missing-column-default` on a generated primary key now has a fix: an identity for an integer key, `gen_random_uuid()` for a `uuid`.
- The pruning check reads the retention of a pg_cron job only when it understands all of its interval: an ISO 8601 interval (`'P1M'`, once read as 1 minute), an unknown unit, a sign or `ago` leaves it unknown, instead of a false `short-changelog-retention` error. `year` and `ms`/`milliseconds` are now understood. Comments in the command of a job are ignored (a commented-out `DELETE` no longer counts as pruning), and its table names are compared as PostgreSQL reads them (a quoted name keeps its case and may contain spaces).
- A changelog function whose comment has the `lilypad-changelog:` prefix but no integer version is reported as `outdated-changelog` (version 1), instead of passing as current.
- `lilypad-doctor` reports `--sql` with `--json`, and an empty `--config`, before it looks for the database URL.
